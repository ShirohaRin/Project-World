# 实时语音对话模块专项开发规则

> 本文件只维护实时语音对话模块特有的详细约定。项目通用规则统一以 [PROJECT_RULES.md](../../PROJECT_RULES.md) 为准；若两者冲突，以项目级规则为准。

## 1. 适用范围

本规则适用于 `Project-IDEA/modules/realtime_voice/` 下全部实时语音对话能力的设计、实现、测试与维护，包括：音频通道、语音识别（ASR）、端点检测、对话编排、语音合成（TTS）与打断控制。

本模块只负责「听到」和「说出」，不负责对话内容的生成策略。文本轮次通过 `server/brain.py` 复用 `server/` 现有的对话实现，不得在本模块内重建一套对话逻辑或另起一套会话记忆。

## 2. 核心文档

[实时语音对话模块设计.md](./实时语音对话模块设计.md) 是本模块的核心文档，同时承担以下职责：

1. 模块目标、使用场景与边界；
2. 协议规范（消息类型、二进制帧格式、版本号）；
3. 会话状态机与打断机制；
4. provider 抽象与选型记录；
5. 与 `server/` 的集成方式；
6. 里程碑、开发进度与验证记录；
7. 已知限制、遗留问题与后续计划；
8. 与参考实现 N.E.K.O 的对照与裁剪记录。

任何功能完成、范围变化或协议调整后，都必须同步维护该文档。不得只改代码而不更新核心文档。

## 3. 目录结构

模块主体目录固定为：

```text
Project-IDEA/modules/realtime_voice/
├── 开发规则.md
├── 实时语音对话模块设计.md
├── contract/
│   ├── __init__.py
│   ├── manifest.json
│   └── protocols.py          # 协议唯一来源
├── server/
│   ├── __init__.py
│   ├── audio/                # 重采样、下行抖动缓冲
│   ├── session.py            # 会话状态机
│   ├── ws.py                 # WebSocket 端点
│   └── <后续：asr/ endpointing/ tts/ brain.py>
└── tests/
```

后续新增的子能力（音频处理、ASR、端点检测、TTS）各自使用独立子目录，不得把尚未确定边界的多项能力混写在同一文件里。

## 4. 协议约定

- [contract/protocols.py](./contract/protocols.py) 是跨端协议的唯一来源。消息类型、二进制帧布局、版本号、校验规则都只在这里定义一次。
- 任何客户端（Android、PC、Web）实现协议时必须以该文件为准；服务端与客户端不得各自维护一份协议副本。
- 协议变更必须提升 `PROTOCOL_VERSION`，并在核心文档的协议章节记录变更内容与兼容性影响。
- 上行控制消息与音频帧必须分离：控制走 JSON 文本帧，音频走二进制帧，不得混用。
- 服务端对不符合协议的输入必须返回明确的 `error` 消息或直接关闭连接，不得静默忽略。

## 5. 音频格式约定

- 上行与下行的 PCM 一律为 **16 位小端、单声道**。
- 采样率由 `hello` 协商，服务端负责重采样；客户端不得假定服务端使用自己发送的采样率。
- 二进制帧必须带轻量帧头（magic + version + frame_type + seq），不得发送裸 PCM。
- 单帧音频时长必须设上限并在解码时强制校验，超限帧一律拒绝。
- 编解码字段（`codec`）从一开始就要保留 Opus 的位置；切换编码属于协议内行为，不得为此改动消息结构。

## 6. 会话与并发约定

- 一个 WebSocket 连接至多承载一个语音会话；并发会话必须使用不同的连接。
- 会话状态只能通过 `server/session.py` 的状态机迁移，禁止在端点层直接改写状态。
- 每一次「助手发声」都必须有唯一的 `speech_id`；打断、结束、错误路径都必须携带该 id，客户端据此丢弃过期音频。
- 打断必须走「取消在途生成 + 作废音频世代 + 通知客户端清空播放队列」三步，不得只依赖向客户端发送一个停止信号。
- 所有取消路径都必须保证资源释放；不得出现在途任务悬挂或 worker 泄漏。

## 7. provider 抽象约定

- ASR 与 TTS 都必须先定义 `Protocol` 接口，再由具体厂商实现；业务编排代码不得直接依赖任何厂商 SDK 或厂商专有字段。
- 首版实现选定阿里云 DashScope，但厂商选择属于可替换实现细节，不得写进状态机或协议。
- 新增 provider 时只允许新增实现文件与注册项，不得修改既有 provider 的行为。
- provider 的密钥只能来自环境变量或 `server/config.yaml` 的 `voice` 段，不得硬编码，也不得写入核心文档与测试。

## 8. 依赖与资源约定

- 默认路径不得依赖本地 GPU、本地大模型或需要用户额外部署的服务；本地算力方案只能作为可选增强。
- 模型文件（VAD 等）不得直接提交进仓库；需要时通过明确的下载与校验流程获取，并在核心文档记录来源、体积与校验方式。
- 新增第三方依赖必须同步写入 `server/requirements.txt`，并说明用途；纯标准库能完成的编解码不得引入额外依赖。

## 9. 开发流程

1. 开发前读取本文件、核心文档与 [PROJECT_RULES.md](../../PROJECT_RULES.md)；
2. 确认当前里程碑与待办项；
3. 先定协议或接口，再写实现；
4. 在模块内实现代码与测试；
5. 运行匹配的测试并如实记录结果；
6. 更新核心文档的进度、验证与已知限制；
7. 未经明确授权，不修改 `server/` 中与语音无关的代码。

## 10. 完成标准

一个里程碑只有在以下内容齐全后才能标记为完成：实现代码、测试、接口或协议契约、关键注释、验证结果、已知限制，以及核心文档的进度更新。
