# 实时语音对话模块设计（核心文档）

> 本文件是实时语音对话模块的唯一核心文档，同时承担「设计说明 + 协议规范 + 开发进度 + 已知限制」四重职责。模块特有开发约定见 [开发规则.md](./开发规则.md)，项目级规则见 [PROJECT_RULES.md](../../PROJECT_RULES.md)。

## 1. 目标与使用场景

为 IDEA 提供端到端的实时语音对话能力：用户说话 → 实时识别 → 对话大脑生成回复 → 流式合成语音 → 边生成边播放，并支持用户在助手说话时打断。

目标使用场景：

- 手机客户端（主要场景）：单一 WebSocket 长连接，弱网可重连；
- PC 客户端：同一协议，可使用更高采样率与文本输入；
- 后续任意新客户端：直接按本文件的协议实现，不需要改服务端。

## 2. 边界

本模块负责：

- 音频通道（上行接收、下行下发、重采样、抖动缓冲）；
- 语音识别与端点检测（判断用户说完了没有）；
- 对话轮次编排（把转写文本交给对话大脑，把回复文本交给语音合成）；
- 语音合成与流式下发；
- 打断控制与会话状态管理。

本模块不负责：

- 对话内容生成（复用 `server/` 现有对话能力）；
- 人格、记忆与工具调用的具体策略（由 `server/` 侧决定）；
- 客户端界面与播放设备管理（客户端侧职责，协议只规定数据契约）。

## 3. 总体架构

```text
客户端（Android / PC / Web）
   │  上行：JSON 控制帧 + 二进制音频帧
   ▼
server/ws.py                 ── WebSocket 端点：握手、鉴权、消息分发
   │
server/session.py            ── 会话状态机：状态迁移、世代管理、打断
   │
   ├─ audio/                 ── 重采样、下行抖动缓冲
   ├─ asr/                   ── 语音识别：provider 抽象 + 具体实现（M2）
   ├─ brain.py               ── 对话桥：复用 server 现有对话实现（M3）
   ├─ tts/                   ── 语音合成：分句、队列、流式下发（M4）
   └─ endpointing/           ── 端点检测：判断一轮说话是否结束（M5）
```

数据流：

```text
麦克风 ─→ 音频帧 ─→ 重采样(16k) ─→ ASR 流式识别 ─→ 转写文本
                                                     │
端点命中 ────────────────────────────────────────────┘
                                                     ▼
                                        对话大脑（流式文本）
                                                     │
                                            分句 ─→ TTS 流式合成
                                                     │
播放 ←── 音频帧 + audio_done ←── 服务端按 speech_id 下发
```

## 4. 协议规范

### 4.1 传输

- 端点：`/ws/voice`（WebSocket）；
- 控制消息：JSON 文本帧，字段 `t` 表示消息类型；
- 音频数据：二进制帧，必须带 8 字节帧头；
- 协议版本：`PROTOCOL_VERSION = 1`，在 `hello` 中协商。

### 4.2 二进制帧格式（8 字节头 + 负载）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | magic | 固定 `b"IV"`（IDEA Voice） |
| 2 | 1 | version | 帧格式版本，当前为 `1` |
| 3 | 1 | frame_type | `1` = 音频帧 |
| 4 | 4 | seq | 本方向帧序号，uint32 小端，从 1 递增 |
| 8 | N | payload | PCM16 小端、单声道原始数据 |

设计取舍：

- **采样率不逐帧携带**，由 `hello` 协商后固定，省去每帧字节开销；变更音频格式必须重发 `hello`；
- **保留 `seq`**：客户端与服务端都能据此检测丢帧、乱序，并为打断后的过期音频判定提供依据；
- **保留 `version` 与 `frame_type`**：未来加入 Opus 帧、控制帧时不需要改帧头结构。

单帧时长上限：**120 ms**（48 kHz 单声道 PCM16 约 11.5 KB）。超限帧一律拒绝并返回 `error`。

### 4.3 上行消息（客户端 → 服务端）

| `t` | 字段 | 说明 |
|---|---|---|
| `hello` | `v` 协议版本；`platform` 平台标识；`codec` 编码；`rate` 采样率；`channels` 声道数 | 连接后必须首先发送；服务端据此校验并协商 |
| `start` | — | 开始一个语音会话，进入可上行音频状态 |
| `text` | `text` | 文本输入（PC 端键盘输入等），与语音输入共用同一轮次编排 |
| `interrupt` | — | 客户端主动打断当前助手发言 |
| `end` | — | 结束本次会话 |
| `ping` | — | 保活，服务端回 `pong` |

`codec` 当前只接受 `pcm16`；`rate` 只接受 `16000` 与 `48000`；`channels` 只接受 `1`。

### 4.4 下行消息（服务端 → 客户端）

| `t` | 字段 | 说明 |
|---|---|---|
| `session_started` | `session_id`；`protocol`；`audio`（协商后的格式） | `hello` 校验通过 |
| `session_ended` | `reason` | 会话结束 |
| `asr_partial` | `text` | 识别中间结果，可覆盖显示 |
| `asr_final` | `text` | 一轮识别的最终结果 |
| `assistant_delta` | `text` | 对话回复的文本增量 |
| `assistant_done` | — | 本轮回复文本结束 |
| `audio_chunk` | `speech_id`；`seq`；`codec`；`rate` | 紧随其后是若干二进制音频帧 |
| `audio_done` | `speech_id` | 该 `speech_id` 的音频已全部下发 |
| `user_activity` | `interrupted_speech_id` | 通知客户端立即清空播放队列并丢弃该 id 的音频 |
| `pong` | — | 对 `ping` 的响应 |
| `error` | `code`；`message` | 协议或运行错误 |

`speech_id` 是打断机制的锚点：客户端只播放当前有效的 `speech_id`，收到 `user_activity` 或新的 `audio_chunk` 时丢弃其余音频。

## 5. 会话状态机

```text
idle ──hello/start──→ listening ──端点命中──→ thinking ──首句就绪──→ speaking
                        ↑                                             │
                        └───────── 用户抢话 / interrupt ───────────────┘
                              （取消在途生成 + 作废世代 + user_activity）
```

| 状态 | 含义 | 允许的输入 |
|---|---|---|
| `idle` | 已连接，未开始会话 | `hello`、`start`、`ping` |
| `listening` | 上行音频，识别中 | 音频帧、`text`、`interrupt`、`end` |
| `thinking` | 已定端点，等待对话回复 | `interrupt`、`end` |
| `speaking` | 下发合成语音 | 音频帧（触发打断）、`interrupt`、`end` |
| `closed` | 会话已结束 | 无 |

状态迁移只允许由上表规定的输入触发，非法输入返回 `error` 而不得静默改变状态。

## 6. 打断机制

打断分三步，缺一不可：

1. **取消在途生成**：取消尚未完成的对话请求与合成任务；
2. **作废音频世代**：`speech_id` 作废 + 世代号递增，此后到达的旧音频一律丢弃；
3. **通知客户端**：下发 `user_activity` 并带 `interrupted_speech_id`，客户端立即清空播放队列。

触发源有两个：服务端在 `speaking` 状态下从上行音频检测到用户持续说话；或客户端主动发送 `interrupt`。

## 7. provider 抽象与选型

ASR 与 TTS 各自定义 `Protocol` 接口，编排层只依赖接口。

首版选型（依据：中文母语、WebSocket 双向流式、首包延迟低、无本地依赖）：

| 能力 | 首版实现 | 备选 |
|---|---|---|
| ASR | 阿里云 DashScope `qwen3-asr-flash-realtime` | 火山豆包、Soniox、OpenAI Realtime |
| TTS | 阿里云 DashScope `qwen3-tts-flash-realtime` | 豆包 `seed-icl-2.0`（自然度与音色克隆）、MiniMax `speech-2.8-turbo` |

选型原则：听感自然、不像导航播报；不引入本地 GPU 依赖；厂商可替换。

## 8. 与 server 的集成

- WebSocket 端点以 `APIRouter` 形式暴露，由 `server/main.py` 注册；
- 鉴权复用 `server/platform_auth.py` 的凭据体系，WebSocket 通过查询参数或首帧提交凭据；
- 对话轮次复用 `server/` 现有的 LLM 客户端与流式实现（函数级复用，不经过 HTTP 回环）；
- 配置新增 `server/config.yaml` 的 `voice` 段，密钥只来自环境变量。

## 10. 已知限制

- 真实语音链路尚未打通：ASR、对话、TTS 都还是空的，目前只有音频输入侧的规范化；
- 重采样是语音级实现（降采样时移动平均抗混叠 + 线性插值），没有多相滤波，也未与 soxr 这类高质量实现做过客观对比；
- 下行抖动缓冲已实现并有单测，但要到 M4 才有音频源接入，尚无端到端验证；
- Opus 编码只在协议中预留字段，未实现；
- 客户端侧实现（Android / PC）尚未开始；
- WebSocket 鉴权目前只有一个可选的环境变量共享令牌，未接入 `server/platform_auth.py` 的凭据体系与审计，需在接入真实语音链路前完成。

## 11. 与 N.E.K.O 的对照

参考来源：`d:\Project World\N.E.K.O`（上游项目）。

| 能力 | N.E.K.O 做法 | 本模块做法 |
|---|---|---|
| WebSocket 端点 | 依赖全局单例 `shared_state`，与桌宠形态耦合 | 重写为 `APIRouter`，无全局单例 |
| 会话管理 | `LLMSessionManager` 由 11 个 Mixin 组装，Mixin 互读彼此属性 | 重写为单一状态机，状态集中管理 |
| TTS 编排 | `Thread` + `queue.Queue` 与 asyncio 混用 | 重写为 asyncio 原生实现 |
| 音频帧 | 每帧带 `NEKO` magic + 采样率 | 保留 magic 思路；采样率改由 `hello` 协商 |
| 端点检测 | silero VAD + smart_turn 语义端点（ONNX，需下载校验） | 借鉴分层思路；模型文件不入库，来源与校验单独记录 |
| 打断 | `speech_id` 轮换 + 前端世代作废 + 麦克风租约 | 借鉴 `speech_id` + 世代作废；麦克风租约按需简化 |
| 音色体系 | `VoiceConfig` 结构化音色 + 多 provider 注册表 | 借鉴数据模型，首版只接一家 |

裁剪原则：只移植依赖封闭、职责单一的部分（协议常量、数据模型、端点检测算法）；与桌宠形态绑定的主动搭话、游戏租约、Steam、截图与桌宠贴图相关代码一律不引入。
