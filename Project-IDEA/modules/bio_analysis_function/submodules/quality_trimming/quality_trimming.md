# quality_trimming：reads 滑窗质量剪切

按质量数据**逐条 read** 决定从哪里切掉测序末端的低质量碱基，输出修剪后的 FASTQ。
算法与 fastp 1.3.x 的 `cut_front` / `cut_right` / `cut_tail` 逐位对齐。

本子模块**可独立使用**：在 IDEA Assistant 的生物计算方法广场中有独立入口
（方法 id `bio-quality-trimming`）。**只需要一份 FASTQ 本身就能运行**——
不需要参考基因组、不需要注释文件、不需要数据库，也不需要先跑别的算法。
代码层面同样可以单独导入，不依赖本模块的其他子模块，也不依赖任何外部程序。

---

## 1. 它解决什么问题

Illumina 测序是边合成边测序。随着循环数增加，三个物理过程会让信号逐渐劣化：
荧光基团的光漂白与残留、簇内分子的相位不同步（phasing）、聚合酶活性衰减。
结果是**一条 read 从头到尾质量单调下降**，末端基本是噪声。

这些末端碱基既不能整条丢弃（前面几百 bp 还是好的），也不能按固定长度裁
（每条 read 的拐点不同，取决于这一簇的物理状况），只能逐条 read 按质量数据本身决定。

**判定的核心概念是 Phred 质量值。** FASTQ 第三行不是文本，而是打包成 ASCII 的
整数数组，每个字符编码一个碱基的错误概率：

```
Q = -10 * log10(P_error)      Q20 -> 1%     Q30 -> 0.1%     Q40 -> 0.01%
字符码 = Q + 33                '!'=0  '5'=20  '?'=30  'I'=40
```

判定用**连续 W 个碱基的平均质量**而不是单碱基，因为测序错误成簇出现，
逐碱基判定会被中间的偶然高值打断。判定条件等价于：

```
窗口内字符码之和  >=  W * (33 + 质量阈值)
```

三种模式的差别只在"找什么、往哪切"：

| 模式 | 扫描方向 | 找什么 | 切到哪里 |
| --- | --- | --- | --- |
| `cut_front` | 5'→3' | 第一个**达标**窗口 | 该窗口之后开始保留 |
| `cut_tail` | 3'→5' | 从右数第一个**达标**窗口 | 保留到该窗口起点 |
| `cut_right` | 5'→3' | 第一个**不达标**窗口 | 只保留该窗口内仍达标的单碱基前缀 |

`cut_right` 比 `cut_tail` 激进得多：会砍掉"局部塌陷之后又好回来"的区域。
**两者同时开启时只执行 `cut_right`。**

完整的数学推导、上游边界行为的取舍理由、以及与上游源码的逐行对应关系，
见 `algorithm.py` 的模块文档字符串，以及
本文件末尾的「附：开发记录」（原《生物方法模块算法清单》5.4.1 节）。

## 3. Python API 用法

### 文件进、文件出（最常用）

```python
from modules.bio_analysis_function.submodules.quality_trimming import (
    QualityCutConfig,
    trim_fastq,
)

summary = trim_fastq(
    "clean_R1.fastq.gz",
    "trimmed_R1.fastq.gz",
    config=QualityCutConfig(enabled_tail=True, window_size_tail=4, quality_tail=20),
)

print(summary.kept_reads, summary.bases_removed, summary.removal_rate)
```

处理是流式的，任何时候内存里只有当前记录，可以直接跑几十 GB 的文件。
默认输出压缩方式**跟随输入**（与输出文件名的扩展名无关，因为文件名可能骗人）；
需要覆盖时显式传 `compress=True/False`。

### 单条 read

```python
from modules.bio_analysis_function.submodules.quality_trimming import (
    QualityCutConfig,
    trim_and_cut,
)

result = trim_and_cut(
    b"TTTTAACCCCCCCCCCCCCCCCCCCCCCCCCCCCAATTTT",
    b"/////CCCCCCCCCCCC////CCCCCCCCCCCCCC////E",
    front=0,
    tail=1,
    config=QualityCutConfig(enabled_front=True, enabled_tail=True),
)

if result is None:
    ...          # 这条 read 应当被丢弃
else:
    print(result.sequence, result.front_trimmed)
```

### 直接读写 FASTQ

FASTQ 流式读写位于模块公共层（`common/fastq.py`），与 `poly_trimming` 等子模块共用：

```python
from modules.bio_analysis_function.common.fastq import read_fastq, write_fastq

for record in read_fastq("sample.fastq.gz"):     # 迭代器，逐条产出
    print(record.name, record.length)
```

`read_fastq` 返回迭代器而非列表——FASTQ 常在 10~50 GB 量级，不能整体读入内存。
gzip 按**魔数**自动识别，不看扩展名。

## 4. 参数

`QualityCutConfig` 的字段：

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `enabled_front` | `False` | 启用 `cut_front` |
| `enabled_tail` | `False` | 启用 `cut_tail` |
| `enabled_right` | `False` | 启用 `cut_right`；与 `enabled_tail` 同时为真时只执行本项 |
| `window_size_front` / `window_size_tail` / `window_size_right` | 4 | 三个模式各自的窗口大小 |
| `quality_front` / `quality_tail` / `quality_right` | 20 | 三个模式各自的质量阈值 |

`trim_and_cut` / `trim_fastq` 另有 `front` / `tail` 两个固定修剪参数（默认 0）。

参数越界（窗口 < 1、质量阈值不在 0~93、`front`/`tail` 为负）会在构造时直接报错，
不会静默取默认值。

## 5. 输出解读

`TrimSummary` 的字段：

| 字段 | 含义 |
| --- | --- |
| `total_reads` | 输入 read 总数 |
| `kept_reads` | 写出的 read 数 |
| `changed_reads` | 其中**序列真的被改动**的条数（质量本来达标的不计入） |
| `dropped_reads` | 剪切后长度不合法而被丢弃的条数 |
| `bases_before` / `bases_after` | 剪切前后的碱基总数 |
| `bases_removed` | 切掉的碱基数（即前两者之差） |
| `removal_rate` | 切掉的碱基占输入总碱基的比例 |

恒等式：`total_reads = kept_reads + dropped_reads`，`kept_reads >= changed_reads`。
`render()` 可以把这些数字渲染成可读文本。

**怎么判断参数是否合适**：先在真实数据上跑一遍看 `removal_rate`。
偏高（例如超过 20%）说明阈值对这批数据太严，或数据本身质量不佳；
接近 0 说明阈值太松，或者这批数据质量确实很好（都属正常，需结合测序报告判断）。

## 8. 已知限制

- **只处理单端 read**。双端 overlap 分析、碱基校正、合并属于后续算法。
- **不理解碱基语义**。只看质量字符与字面量 `N`（仅识别大写），不做接头识别，
  也不判断序列的生物学含义。
- **会破坏下游去重的精确匹配**。fastp README 明确警告：`cut_front` 与 `cut_tail` 会让
  "原本在坐标区间上完全相同的两条 read"变得不同，而去重依赖这种精确匹配。
  做去重时需要重新评估剪切策略。
- **质量阈值是绝对标准，不随数据自适应**。同一套参数在不同质量的样本上剪切比例可能差异很大，
  这是预期行为。
- **刻意保留上游的三处"怪"行为**，不做改良：`cut_front` 把命中的好窗口一起切掉；
  `cut_tail` 全窗口不达标时只保留 1 个碱基（随后交由过滤环节按长度丢弃）；
  扫描未命中时返回 `for` 循环的自然退出值。理由见 `algorithm.py`。
- **实际计算执行链路尚未接通**。广场上的入口目前只到契约层。
- **性能未做基准**。单线程纯 Python，未做批量化或并行化；千万级 read 的样本需要重新评估。

#### 5.4.1.1 选择依据

1. **它是 fastp 处理链里第一个真正需要算法设计的步骤**。上游对单条 read 的处理顺序是：UMI → 固定位置修剪 → **滑窗质量剪切** → polyG/polyX → 接头检测与裁剪 → 过滤 → 统计 → 去重。前三项里，UMI 与固定位置修剪都只是"从第 N 个碱基切掉"，只有滑窗剪切需要根据数据本身逐条 read 计算切点。
2. **它是唯一能拿到"逐位可验证真值"的算法**。上游 `src/filter.cpp` 自带单元测试向量，输入与期望输出都是写死的，因此本实现不是"看起来对"，而是可以逐位比对。这在生物算法里是很奢侈的验证条件。
3. **零外部依赖**。纯数值计算，不需要参考基因组、不需要数据库、不需要比对引擎、不需要编译器，是整条线里唯一完全自足的算法。
4. **它是全部下游的前置**。质控后的 reads 是后续比对与变异检测的输入，这一步的边界行为会一路传递下去。

#### 5.4.1.3 问题定义与算法原理

**为什么末端质量必须按数据切、而不能按固定长度切。** Illumina 测序是边合成边测序。随着循环数增加，三个物理过程会让信号逐渐劣化：荧光基团的光漂白与残留、簇内分子的相位不同步（phasing / pre-phasing）、聚合酶活性衰减。结果是**一条 read 从头到尾质量单调下降**，末端基本是噪声。这些末端碱基既不能整条丢弃（前面几百 bp 仍是好的），也不能按固定长度裁（每条 read 的拐点不同），只能逐条 read 按质量数据本身决定。

**Phred 质量值。** FASTQ 第三行不是文本，而是打包成 ASCII 的整数数组，每个字符编码一个碱基的错误概率估计：

$$
Q = -10\log_{10} P_{\text{error}}
\qquad\Longleftrightarrow\qquad
P_{\text{error}} = 10^{-Q/10}
$$

$Q=20$ 对应 1% 错误率，$Q=30$ 对应 0.1%，$Q=40$ 对应 0.01%。取对数是因为错误是独立事件、概率相乘，取对数后变成相加，避免连乘下溢。存储采用 Phred+33：字符码 $c = Q + 33$，所以 `!`$=0$、`5`$=20$、`?`$=30$、`I`$=40$。

**为什么用窗口平均而不是单碱基判定。** 测序错误成簇出现：某个位置信号塌陷时往往连续几个碱基都低，中间可能偶然冒一个高值。逐碱基判定会被这种噪声打断，切在错误的位置。改为判断连续 $w$ 个碱基的平均质量是否达标：

$$
\frac{1}{w}\sum_{i=s}^{s+w-1} Q_i \ge Q_{\text{thresh}}
$$

两边同乘 $w$、再代入 $Q_i = c_i - 33$（$c_i$ 为字符码）：

$$
\sum_{i=s}^{s+w-1} c_i \ge w\,(33 + Q_{\text{thresh}})
$$

**这正是上游源码里的** **`totalQual >= w * (33 + q)`**——它不是优化技巧，而是上面不等式的精确等价形式，只是为了避开浮点除法。

**三种模式的区别。** 三者共用同一套窗口判定，区别只在找什么、往哪切：

| 模式          | 扫描方向  | 找什么            | 切到哪里                         |
| ----------- | ----- | -------------- | ---------------------------- |
| `cut_front` | 5'→3' | 第一个**达标**窗口    | 该窗口之后开始保留（连这个好窗口也切掉，`s+w-1`） |
| `cut_tail`  | 3'→5' | 从右数第一个**达标**窗口 | 保留到该窗口**起点**（该窗口本身保留）        |
| `cut_right` | 5'→3' | 第一个**不达标**窗口   | 只保留该窗口内仍达标的单碱基前缀，其余全切        |

`cut_right` 明显比 `cut_tail` 激进：它会砍掉"局部塌陷之后又好回来"的区域。**两者同时开启时只执行** **`cut_right`**，这是上游的明确行为。

**剥 N。** 剪切完成后还要剥掉紧邻的前导 / 尾部 `N`。`N` 表示测序仪无法判定碱基，低质量区常以 N 结尾，留着会干扰下游比对。注意这里只识别大写 `N`（与上游一致）。

#### 5.4.1.4 工程实现

**滚动求和。** 窗口每右移一位，只需"右端进一个、左端出一个"两次加法，整体复杂度从 $O(nw)$ 降到 $O(n)$。实现位于 `_scan_forward`（窗口用起点表示）与 `_scan_backward`（窗口用终点表示，对应 `cut_tail` 的反向扫描）。

**为什么不用 NumPy。** 本子模块刻意使用纯 Python 而非向量化实现，这是一个明确的取舍：

1. 本算法的本质是"找一个边界"，而上游的边界语义非常微妙——循环的自然退出值被后续判断依赖、"是否把命中的窗口一起切掉"在两个模式里不对称、窗口内还要逐个检查单碱基质量。用前缀和 + `argmax` 表达这些语义，需要额外补偿逻辑，反而更容易出错。逐行翻译能保证控制流与上游一一对应。
2. `quality` 以 `bytes` 传入，逐字节索引已经足够快；对 151bp 这类典型读长，单条 read 的开销在微秒量级。
3. 上游是 C++ 实现，Python 侧即便向量化也追不上，与其追求常数优化，不如先把正确性和可对照性做到位。

**刻意保留的上游行为。** 以下几处"看起来奇怪"的逻辑按上游原样保留，不做"改良"：

- `cut_front` 把命中的好窗口一起切掉（切点取 `s + w - 1`），比理论最优多切 $w-1$ 个碱基；
- 反向扫描未命中时，`cut_tail` 的结果是**只保留 1 个碱基**而不是丢弃；
- 扫描未命中时返回的是循环的自然退出值，后续判断直接依赖这个值。

**输入校验。** `sequence` 与 `quality` 必须是等长字节串，`front` / `tail` 不得为负，窗口不小于 1，质量阈值在 $[0, 93]$ 内（Phred+33 的字符上限对应 $Q=93$）。校验只在系统边界做，内部辅助函数不加检查以免拖慢热路径——其前置条件写在 docstring 里。

**FASTQ 读写与流式管道（已上移到公共层）。** 这一层最终落在 `common/fastq.py`：流式读取（返回迭代器，任何时候内存里只有当前记录，以应对 10\~50 GB 量级的样本）、写出、按魔数识别 gzip，以及通用的"读 → 逐条变换 → 写"管道 `process_fastq()`。按模块分层纪律，公共能力需要至少出现两个真实使用方后才提取——$5.4.2$ 的 poly 修剪成为第二个使用方后，这一层便从本子模块整体上移。本子模块的 `runner.py` 现在只做粘合：把配置包装成一个逐条变换函数交给公共管道。

**文件级接口。** `runner.py` 把算法层接到公共层的流式管道上，形成"FASTQ 文件进、FASTQ 文件出"的完整能力，并返回公共层的 `FastqStreamSummary`（read 数、碱基数、剪切比例与几个派生量）。两个边界行为值得记录：输出压缩默认**跟随输入**而不是输出文件名的扩展名（文件名可能骗人，这一点已用故意错配扩展名的测试固定）；若中途失败，已写出的部分输出会被删除，避免留下看似完整实则残缺的结果文件。

**算法广场入口。** 规则 $3.1$ 定义的"独立可用"是产品层面的独立：用户在算法广场里单独选中本算法、按它自己的输入表单填参数、拿到它自己的输出，不需要先跑别的算法，也不要求外部预先处理过数据。本算法已在 `IDEA Assistant Code/src/compute.ts` 的 `COMPUTE_METHODS` 中登记为 `BIO_QUALITY_TRIMMING_METHOD`（id `bio-quality-trimming`，分类"序列预处理"，`local`，`beta`）。界面按 `inputSchema` 自动渲染输入表单，共 6 项：reads 文件、剪切模式（4 个选项）、窗口大小、质量阈值、头部固定修剪量、尾部固定修剪量；输出按 `outputDescription` 展示为"修剪后的 reads 文件引用 + 统计摘要"。**输入是自洽的**——只需要一份 FASTQ，不依赖参考基因组、注释、数据库，也不要求上游先做过处理，因此用户可以单独把它跑起来。

本文件分两部分：前半（第 1~7 节）是**使用说明**——算法做什么、广场入口与输入输出、Python API 用法、参数表、输出解读、验证方式与已知限制；后半「附：开发记录」是**设计文档**——选择依据、算法原理、工程实现、验证记录与待办。

| --------------------------------------------------------------------------------------- | ----------------------------------------------------- | --------------------------------------------------- | ------ |
| `TTTTAACCCCCCCCCCCCCCCCCCCCCCCCCCCCAATTTT` / `/////CCCCCCCCCCCC////CCCCCCCCCCCCCC////E` | `front=0, tail=1, 窗口=4, Q20`，`cut_front` + `cut_tail` | 序列 `C`$\times 28$，质量 `CCCCCCCCCCC////CCCCCCCCCCCCC` | ✓ 完全一致 |

**真实数据验证。** 数据来源为 fastp 仓库自带的 `testdata/R1.fq`（MIT 许可），已固定为本模块共享测试数据 `tests/data/fastp_R1.fq`：真实 Illumina 单端数据，9 条记录，其中第 1 条长度为 0（上游数据里确实存在该边界记录），其余 8 条长度均为 151bp。

| 配置                   | 8 条 read 的剪切后长度                        | 说明              |
| -------------------- | -------------------------------------- | --------------- |
| `cut_tail`，窗口 4，Q20  | 全部 151                                 | 这批数据尾部质量达标，不该切  |
| `cut_tail`，窗口 4，Q30  | 151, 143, 151, 143, 151, 143, 151, 151 | 3 条各去掉 8bp      |
| `cut_tail`，窗口 4，Q35  | 151, 130, 151, 130, 151, 130, 151, 151 | 同样 3 条，各去掉 21bp |
| `cut_right`，窗口 4，Q20 | 88, 41, 151, 41, 151, 41, 151, 151     | 明显更激进           |

三点结论：阈值升高时被切的始终是同一批 read，说明这是数据本身的尾部质量特征而非随机波动；`cut_right` 在真实数据上比 `cut_tail` 激进得多，且逐条满足"保留长度不超过 `cut_tail`"；长度为 0 的记录被正确地判为丢弃（窗口放不下），而不是返回空 read。

#### 5.4.1.6 适用边界与已知限制

- **只处理单端 read**。双端的 overlap 分析、碱基校正、合并属于后续算法，不在本模块范围。
- **不理解碱基语义**。算法只看质量字符与字面量 `N`，不判断序列的生物学含义，也不做接头识别。
- **会破坏下游去重的精确匹配**。上游 README 明确警告：`cut_front` 与 `cut_tail` 会让"原本在坐标区间上完全相同的两条 read"变得不同，而去重算法依赖这种精确匹配。因此去重效果取决于剪切策略的选择，做去重时必须重新评估。
- **质量阈值是绝对标准，不随数据自适应**。Q20 在高质量数据上可能一个碱基都不切，在低质量数据上可能切掉大半，这是预期行为而非缺陷。
- **性能不及上游**。上游为 C++ 多线程 + SIMD，本实现为单线程纯 Python。当前未做基准测试，也未做批量化或并行化；在千万级 read 的样本上需要重新评估。
- **`cut_tail`** **全窗口不达标时只保留 1 个碱基**，随后交由过滤环节按长度丢弃。这是上游的真实行为，本实现按原样保留并已用测试固定。
