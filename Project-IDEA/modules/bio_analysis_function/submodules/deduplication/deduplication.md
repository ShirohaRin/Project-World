# deduplication：重复检测与去重

用**布隆过滤器**判断哪些 read（或 read 对）与前面出现过的重复，报出重复率，
并可选择把重复的丢掉。算法与 fastp 1.3.x 的 `Duplicate`（`src/duplicate.cpp`）
逐位对齐——哈希表、素数表、位图布局全部照抄。

本子模块**可独立使用**：在 IDEA Assistant 的生物计算方法广场中有独立入口
（方法 id `bio-deduplication`）。**只需要一份（或一对）FASTQ 本身就能运行**——
不需要参考基因组、不需要注释文件、不需要数据库，也不需要先跑别的算法。
代码层面同样可以单独导入，不依赖本模块的其他子模块，也不依赖任何外部程序。

---

## 1. 它解决什么问题

测序数据里的"重复"有两种来源，本算法处理的是第一种：

| 来源 | 含义 | 该由谁处理 |
| --- | --- | --- |
| **序列重复** | 两条 read 的碱基完全一样，很可能来自同一个原始 DNA 分子的多次扩增 | **本算法** |
| **同源重复** | 基因组本身就有多拷贝区域，不同分子读出同样的序列 | 本算法**无法**区分，这是它固有的局限 |

重复率过高会让下游出问题：定量会被少数分子放大、变异检出会出现假阳性信号。
很多分析流程的第一步就是看一眼重复率、必要时去掉重复。

做法是**布隆过滤器**——不为每条序列存原文，而是：

1. 把序列压成若干个 64 位整数（"位置向量"）：逐个碱基用一张素数表做乘法累加；
2. 把这些整数对位图取模、把对应比特置 1；
3. 一条序列**所有**位置上的比特在本次运行中**都已经被置起**，就判为重复。

好处是内存固定、与数据量无关（档位 1 就是 1 GiB，看 100 亿条也是 1 GiB）。
代价是**假阳性**：两条不同的序列可能撞到同一组比特上，被判成重复。
见第 3 节。

> **它不做 UMI 去重。** 只按"序列是否一样"判重。真要区分 PCR 重复与真重复，
> 得先用 [`umi_processing`](../umi_processing/umi_processing.md) 把 UMI 提到名字里，
> 再按 UMI 分组——那是另一条路线，本算法不掺和。

## 2. 顺序依赖性（用之前必须知道）

**一条 read 是否被判为重复，取决于它前面出现过什么。**

布隆过滤器只有"见过 / 没见过"两态，没有计数。所以：

```text
A A A  →  第 1 条不重复，第 2、3 条判为重复
A B A  →  第 1、2 条不重复，第 3 条判为重复
```

同一组 read 换个顺序，重复条数就可能不同。这不是 bug，是这类判重的定义。

由此引出两条产品上很重要的性质：

- **本实现严格按文件顺序判定**，因此**同一份输入任何时候跑，结果完全一样**
  （哪些条被丢、丢了几条、重复率是多少，都是数据的确定函数）。
- **本算法没有 `threads` 参数**。它无法并行判定——位图是跨 read 累积的共享状态，
  分给多个线程算就会让"谁先谁后"变成随机的，结果不可复现。这也是
  `common/native` 里唯一不走并行流水线的算法（见
  [native.md](../../common/native/native.md) 的 5.4.0.5.2）。

> **与上游的一处如实差别**：fastp 在 worker 线程里调用 `Duplicate::checkPair`，
> 所以**同一份数据换线程数，它报出的重复率会变**。本实现不会。这是刻意的选择，
> 不是实现差异——我们宁可牺牲并行度，也要保住"结果可复现"。

## 3. 内存档位与假阳性

档位是**产品参数**：多花内存换更低的假阳性，数值与上游一致。

| 档位 | 缓冲区 | 位图总量 | 默认用于 |
| --- | --- | --- | --- |
| 1 | 2 × 512 MiB | **1 GiB** | 只评估重复率 |
| 2 | 2 × 1 GiB | 2 GiB | — |
| 3 | 4 × 1 GiB | **4 GiB** | 去重（默认） |
| 4 | 4 × 2 GiB | 8 GiB | — |
| 5 | 4 × 4 GiB | 16 GiB | — |
| 6 | 8 × 4 GiB | 32 GiB | — |

去重默认比只评估高一档（3 而非 1），因为**判错了要丢数据**——只评估判错只是数字
不准，去重判错是真的把一条好 read 扔了。上游同样这么选。

**假阳性有多大。** 每个缓冲区的比特数为 $B$，看了 $n$ 条之后某一位仍为 0 的概率
约为 $e^{-n/B}$，占用率 $p = 1 - e^{-n/B}$；本实现要所有缓冲区**都**撞上才算重复，
理想均匀哈希下假阳性的量级是 $p^2$：

| 数据量 | 档位 1（$2^{32}$ 比特/缓冲区） | 档位 3（$2^{33}$） | 档位 6（$2^{35}$） |
| --- | --- | --- | --- |
| 1000 万条 | $5.4\times10^{-6}$ | $1.4\times10^{-6}$ | $8.5\times10^{-8}$ |
| 1 亿条 | $5.3\times10^{-4}$ | $1.3\times10^{-4}$ | $8.4\times10^{-6}$ |

以上是**理想均匀哈希的估量级**，不是精确承诺。实测（把位图压小以放大效应）表明
**真实假阳性比这个估计更低**，约低到一半上下——因为位置向量的分布并不均匀，
不像理想哈希那样铺满整个位图。

> **位图大小与结论强相关。** 位置向量要对位图取模，位图小了碰撞自然多。
> 因此两侧实现对拍时必须传同一个位图大小；也正因如此，把位图压小是
> **放大假阳性、压力测试判重实现**的好办法（测试里就这么用）。

## 5. Python API 用法

### 只评估重复率

```python
from modules.bio_analysis_function.submodules.deduplication import deduplicate_fastq

summary = deduplicate_fastq("clean_R1.fastq.gz")
print(summary.total_reads, f"{summary.duplicate_rate:.1%}")
print(summary.render())
```

不给输出路径就是只评估——**不产出任何文件**，也不会去动目录里的同名的旧文件。

### 评估并去重

```python
summary = deduplicate_fastq(
    "clean_R1.fastq.gz",
    "deduped_R1.fastq.gz",
    accuracy_level=3,          # 4 GiB 位图；省略则去重默认就是 3
)
print(summary.kept_reads, summary.dropped_reads)
```

### 双端

```python
summary = deduplicate_fastq(
    "clean_R1.fastq.gz",
    "deduped_R1.fastq.gz",
    read2_path="clean_R2.fastq.gz",
    output2_path="deduped_R2.fastq.gz",
)
```

一级一对 read 被**首尾相接**后一起判重，重复时**成对丢弃**，两份输出始终对齐。

### 单条序列（不读写文件）

```python
from modules.bio_analysis_function.submodules.deduplication import DuplicateDetector

detector = DuplicateDetector(accuracy_level=1, buffer_bytes=1 << 20)  # 测试用小位图
print(detector.check_read(b"ACGTACGTACGT"))   # False，第一次见
print(detector.check_read(b"ACGTACGTACGT"))   # True，重复
print(detector.duplicate_rate)
```

一个实例就是**一次运行的全部记忆**，换数据集要新建实例——否则上一批的比特还留着，
后面的数据会凭空多出重复。

### 原生实现（跑大样本用这个）

Python 版同时是**可逐位对拍的规格**；真实样本用原生层，它位于模块公共层
`common/native/`：

```python
from modules.bio_analysis_function.common.native import deduplicate_fastq

summary = deduplicate_fastq("clean_R1.fastq.gz", "deduped_R1.fastq.gz")
print(summary.kept_reads, summary.accuracy_level)
```

参数与子模块版一一对应，只有两点写法不同：`accuracy_level` 传 `0` 表示
"按模式取默认"，`buffer_bytes` 传 `0` 表示"按档位取值"（两者都是 C ABI 的约定）。
返回值 `NativeDeduplicationSummary` 多一个 `accuracy_level`（C 侧回填实际用的档位，
所以"默认值"只有一处定义）。

## 6. 参数

| 参数 | 默认 | fastp 参数 | 说明 |
| --- | --- | --- | --- |
| `output1_path` / `output2_path` | `None` | `--dedup` 的有无 | 留空 = 只评估；给出 = 去重并写出 |
| `read2_path` | `None` | `-2` | 给了就是双端；与 `output2_path` 要么都给、要么都不给 |
| `accuracy_level` | 按模式 | `--dup_calc_accuracy` | 内存档位 1~6，`None` = 只评估取 1、去重取 3 |
| `buffer_bytes` | `None` | —（本实现新增） | 覆盖每个缓冲区的字节数，见下 |
| `compress` | 跟随输入 | — | 输出是否 gzip |

**`buffer_bytes` 是本实现新增的口子**，上游没有：它覆盖档位给出的"每个缓冲区多大"
（缓冲区个数仍由档位决定）。两个用途：小内存机器上压低头寸；以及**两侧对拍时
指定同一份配置**——位图大小直接决定位置向量的取模结果，进而决定假阳性率，
改小了结论就变，所以对拍必须同值。

`fastp` 还有 `--dont_eval_duplication`（完全不算重复率）。本实现没有这个开关：
**不想要这个结果就别跑这个算法**，算法级的开关在这里没有意义。

## 7. 输出解读

`DuplicationSummary` 的字段：

| 字段 | 含义 |
| --- | --- |
| `total_reads` | 输入条数；双端时是 **read 对数**（`paired` 指出是哪一种） |
| `duplicate_reads` | 判为重复的条数（双端时是对数） |
| `kept_reads` | `total_reads - dropped_reads` |
| `dropped_reads` | **只在真去重时非零**；只评估时恒为 0（那时没丢任何东西） |
| `bases_before` | 输入碱基总数（双端含 R1 与 R2） |
| `bases_after` | **保留下来的**碱基数（输入减去被判重复的那些），与是否写文件无关 |
| `duplicate_rate` | 属性，重复率 |
| `kept_rate` | 属性，保留比例 |
| `accuracy_level` | 实际使用的内存档位 |

两个容易看错的地方，再说一遍：

- 只评估时 `dropped_reads` 是 0、`kept_reads` 等于总数——**不是"没检出重复"**，
  重复条数看 `duplicate_reads`。
- `bases_after` 是"**如果**去重会剩下多少碱基"。去重时它恰好等于写出文件的碱基数；
  只评估时它是假想值，正好用来回答"去重会削掉多少数据"。

**怎么判断参数是否合适**：`duplicate_rate` 高不等于数据坏。文库的重复率与测序深度
强相关——深度越高，同一个分子被测到的次数越多，重复率自然上去。要判断"是不是
PCR 过度扩增"，得和**相同深度、相同建库方式**的历史数据比。真要区分，只能靠 UMI。

## 8. 与 fastp 的对应关系

| 本子模块 | fastp |
| --- | --- |
| `DuplicateDetector` | `Duplicate`（`src/duplicate.cpp`） |
| `check_read` / `check_pair` | `Duplicate::checkRead` / `checkPair` |
| `sequence_positions` | `Duplicate::seq2intvector` |
| `_apply_bloom_filter` | `Duplicate::applyBloomFilter` |
| `generate_prime_table` | `Duplicate::initPrimeArrays` |
| `accuracy_level` / 档位表 | `--dup_calc_accuracy` 与构造函数里的内存表 |
| `deduplicate_fastq` | 处理链里"判重 → 写出"那一段 |

**四处口径按上游原样保留**，不要"顺手改对"——它们都是这个哈希能工作的前提：

1. **素数表是"每万个数的区间里取第一个素数"**，从 10001 起，找到一个素数就跳过
   剩下 9999 个数。**不是"前 N 个素数"**。写错了哈希位置全错，而错的结果
   **看起来仍然像合理的随机哈希**（重复率数字依然像样）——这是全模块最难自查的
   一处，必须有对照向量才能发现。本模块的做法是：Python 侧硬编码上游前 8 项素数，
   原生侧用"极小位图 + 全独特序列"做逐位对拍（见第 9 节）。
2. **uint64 回绕**。C 侧是无符号整数，累加溢出就是取模；Python 是无限精度，
   必须显式 `& (2**64 - 1)`。漏了这一步两侧结果就不同。
3. **位置与碱基值耦合**。累加的是 `prime × (碱基权重 + 位置)` 而不是
   `prime × 碱基权重`——否则 `AAC` 与 `ACA` 会撞在一起。
4. **不短路**。判定时哪怕已经知道这条是新序列，剩下的缓冲区也照样要置位；
   否则后面的 read 看不到这条序列留下的痕迹。

另有一处**上游的行为，看着像 bug 但不是**：碱基权重表只对**大写** `ACGT` 给
7 / 74 / 31 / 222，其余字符（包括小写碱基与 `N`）**一律 13**。因此一段 `aaaa`
与一段 `NNNN` 会被判为互相重复。本实现照抄，并用测试固定住——将来若有人想
"顺手改对"，会先看到那条测试。

**为什么"两次都判对"还不够。** 上面那些用例里绝大多数 read 本来就是真重复，
**哈希怎么变都判得出来**——它们锁不住哈希实现。所以另有一条专门的用例：
**3000 条互不相同的 60bp 序列 + 512 字节的极小位图**。此时真重复为零、
假阳性大量出现，"哪几条被判为重复"**完全**由哈希的每一位决定。

这条用例是**做过故障注入验证的**：把原生侧的素数表改成"从 10001 起的前 N 个素数"
（而不是上游的"每万区间取第一个素数"）后重编译，**只有这条用例失败**，
其余 14 条照样通过；改回即全绿。这证明了它的强度，也证明了常规用例确实锁不住哈希。

## 10. 已知限制

- **假阳性不可消除**，只能靠加大位图压低（见第 3 节）。判错的后果是丢掉一条本不
  重复的 read。
- **判不出"真重复"还是"PCR 重复"**。它只知道两条序列一样，不知道它们来自
  一个分子还是两个。要区分必须用 UMI。
- **判定顺序相关**（第 2 节）。同一份数据换个顺序，重复条数会变；这也意味着
  **不能把大文件切块并行处理再合并结果**。
- **小写碱基与 `N` 在哈希下不可区分**（权重都是 13）。这是上游行为，照抄了。
- **无法并行判定**，因此没有 `threads` 参数，多核机器上这一环吃不到并行红利。
- **默认档位要 1~4 GiB 内存**，桌面客户端上属于"不小的开销"，界面上必须如实
  告诉用户（档位就是为这件事存在的）。
- **实际计算执行链路尚未接通**。广场上的入口目前只到契约层。

## 附：开发记录

### 5.4.11.1 选择依据

1. **它是 fastp 预处理线里最后一块"改数据"的功能**。前面的过滤、裁剪都只看单条
   read 自身的质量，"重复"是**跨 read 的关系**——到目前为止所有算法都不需要记住
   历史，这是第一个需要的。
2. **它是产品上最容易被误读的一步**。用户看到"重复率 30%"会以为数据坏了，
   其实多半只是测序深度高。因此这一项的**解释职责比计算职责更重**：文档必须写清
   假阳性、顺序依赖、以及与深度的关系。
3. **上游源码自包含且可逐行对照**（`Duplicate` 一个类、约 170 行），可以做到与
   前面几个算法一样的逐位对齐。
4. 它也是**唯一不能进并行流水线**的算法（判定依赖全部历史），结构上一次新的尝试。

### 5.4.11.3 工程实现

**单端与双端共用一条 C ABI 入口。** `bio_deduplicate_fastq` 收四个路径
（R1 / R2 / 输出1 / 输出2）：`read2` 为空即单端，`output1` 为空即只评估。
这与 UMI 的做法一致——两个算法都是"单双端同构、只差一个 R2"，
开两个入口只会让调用方多写一遍分支。

**双端为什么是"首尾相接"，而不是"分别哈希再合并"。** 上游把 R1 的位置向量算完
之后，**在同一个数组上**继续累加 R2，且 R2 的位置从 `len(R1)` 起算（`pos_offset`）。
这等价于把两条 read 连成一条虚序列再哈希。好处是"调换 R1/R2 不算同一对"——
位置不同，位置向量自然不同。

**"只评估"与"去重"共用一遍扫描。** 两种模式唯一的差别是"要不要写文件"，
因此实现里只有一个循环，用一个 `writing` 标志控制是否写出、以及是否把判为重复的
那条计入 `dropped`。这避免了"统计口径在两种模式下不一致"这类经典问题。

**失败时删半成品。** 与其余算法同一套：writer 声明在 `try` 内部，异常时先随栈展开
析构（关闭文件句柄），`catch` 里再删——Windows 上打开中的文件删不掉。
双端时**两个半成品都删**。

**Python 侧的 `buffer_bytes` 与 C 侧的对应。** 两边都提供了覆盖位图大小的口子，
且都只覆盖"每个缓冲区多大"、不动缓冲区个数。这样对拍时两侧能构造出完全相同的
配置，而生产路径不受影响。

### 5.4.11.4 验证记录

Python 侧 **48 项**、原生对拍 **15 项**，全部通过。

**素数表单独固定。** 上游前 8 项是 `10007, 20011, 30013, 40031, 50033, 60037,
70039, 80051`——写成"前 8 个连续素数"的话会是 `2, 3, 5, 7, 11, 13, 17, 19`，
一眼可辨。Python 侧硬编码这 8 项；原生侧靠下面那条对拍用例。

**回绕单独固定。** 正常数据下累加值离 $2^{64}$ 很远（要有几百万个碱基的序列才
自然溢出），所以测试里**把素数表临时换成 $\approx 2^{62}$ 的量级**，一次累加就越界——
这条测的才是"有没有取模"，而不是"值恰好很大"。

**交叉验证。** 位置向量另写一份"用 Python 任意精度累加、最后统一取模"的朴素实现
（模运算对加法与乘法同态，两者应当等价），在 200 组随机数据上对比。

**故障注入。** 见第 9 节末尾：把原生侧素数表改成"前 N 个连续素数"后，
**只有**"极小位图 + 全独特序列"那条用例失败，其余 14 条通过；改回即全绿。
这一步是必要的——最初版本的"极小位图"用例用的是**含大量真重复**的数据，
故障注入后照样通过，说明它根本没测到哈希。
