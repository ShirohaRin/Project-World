# read_mapping：参考比对（read mapping）

把 reads 比到参考序列上。这是参考比对与变异检测线里**第一个真正的算法**，
也是最难的一块——breseq 整条链的入口就是它（上游用的是 bowtie2）。

> **当前状态：A–F 全部分片完成。** 已完成 **A · k-mer 种子索引**、**B · 种子投票与候选对角线**、
> **C · 带内比对（允许短 indel）与 CIGAR**、**D · 软剪裁与末端处理**、
> **E · 多重命中/MAPQ 与 SAM 输出**、**F · 端到端对拍与性能实测**：对一条 read 能给出参考名、
> 0-based 起点、链方向、CIGAR（含 S）、错配/插入/缺失/软剪裁明细与映射质量，能把结果
> **写成 IGV 可打开的 SAM**，并且有成规模的合成读集对拍（召回、精确度、误报、MAPQ 校准）
> 与可复现的性能实测（`tools/benchmark.py`）。算法广场上的入口仍是**只登记调用契约**——
> 执行链路未接通，见「已知限制与待办」。

## 1. 现在能做什么

| 项 | 内容 |
| --- | --- |
| 输入 | 一组参考序列（染色体 + 质粒）+ 若干 `Read`（名字、序列、质量、是否 read2） |
| 输出 | 每条 read 的 `Alignment`（参考名、起点、链方向、**CIGAR**、错配/插入/缺失/软剪裁数、**MAPQ**、票数、候选数）或"未比对" |
| 落盘 | `write_mapped_sam(...)`：写出一份含 `@HD/@SQ` 头、`NM` 与 `MD` 标签的 SAM |
| 另可用 | `SeedIndex` / `ReferenceIndex`（k-mer → 位置）、`align_banded`（带状局部比对）、`build_md_tag`、`tools/benchmark.py`（建索引与比对的耗时/内存实测） |

## 2. Python API 用法

```python
from modules.bio_analysis_function.common.reference_io import read_genbank
from modules.bio_analysis_function.submodules.read_mapping import (
    Mapper, MappingParams, Read, ReferenceIndex, SeedIndex, decode_kmer, encode_kmer,
)

reference = read_genbank("NC_001422.gbk")
sequence = reference.get("NC_001422").sequence

# 索引（可复用：同一份参考的索引比对多批 reads 时只建一次）
index = ReferenceIndex.build(reference, k=16, step=4)
print(SeedIndex.build("NC_001422", sequence, k=16, step=4).stats())   # 单条序列的统计量

# 比对
mapper = Mapper(reference=reference, index=index, params=MappingParams(seed_length=16, step=4))
alignment = mapper.map_read(Read(name="r1", sequence=sequence[4000:4100]))
print(alignment.seq_id, alignment.reference_start, alignment.strand,
      alignment.cigar, alignment.mismatches, alignment.insertions, alignment.deletions)
print(alignment.edit_distance, alignment.identity, alignment.is_gapped)

# 带内比对也可以单独用（自己给窗口与期望对角线）
from modules.bio_analysis_function.submodules.read_mapping import align_banded
print(align_banded("AAACGGG", "AAACCCGGG", window_start=0, center=0, max_indel=3).cigar)

# 批量：输出与输入一一对应（比不上的位置是 None），顺序不变
for read, result in zip(reads, mapper.map_reads(reads)):
    print(read.name, "未比对" if result is None else result.reference_start)
```

## 3. 参数

| 参数 | 默认 | 含义与取舍 |
| --- | --- | --- |
| `seed_length` | 16 | 种子长度。越大越特异、命中越少，但越容易被一个错配打断 |
| `step` | 4 | 建索引步长。1 = 逐位建。**稀疏只降灵敏度、不伤正确性**，条件见第 4 节 |
| `max_hits` | 64 | 单 k-mer 的位置数上限，超过则**整条剔除**（理由见第 4 节） |
| `max_mismatches` | 4 | 允许的错配数上限。**不能调太紧**：真实变异位点在 read 上就是错配，调紧会把变异连同比对一起丢掉 |
| `max_indel` | 3 | 带宽：允许的净漂移，同时也是"插入碱基 + 缺失碱基"之和的上限 |
| `max_clip` | 10 | 每端最多软剪裁多少碱基（接头读通、质量掉尾）。0 表示关掉末端处理 |
| `max_candidates` | 8 | 最多扩展几条候选对角线（按票数排序后的前若干条） |

**完全匹配的快路**：如果某条候选在无缺口下完全匹配，它的编辑距离已经是 0、不可能更好，
于是直接采用、不再做动态规划。这不改变结果（只是快），真实数据里多数 read 走这条路。

## 4. 四条必须知道的约定

1. **坐标是 0-based**，`Alignment.reference_start` 是"read 第 0 位落在参考的坐标"。
   与 `reference_io`、SAM 的 1-based 口径不同——换算发生在取用坐标的地方（比如写 SAM 时）。

2. **负链比对的序列是"反向互补之后"的那条**（SAM 也是这个口径：FLAG 0x10 时 SEQ 存正向
   参考方向）。因此扩展时统一拿"与参考同向"的序列逐位比对，不需要分情况处理。

3. **稀疏索引成立的条件**。设真实比对的对角线为 `d`（参考位置 = d + read 偏移）：
   窗口落在 `≡ 0 (mod step)` 的参考位置上，所以只要 read 在真实对角线上存在一段
   **长度 ≥ step 的连续完全匹配**，其中必有一个 read 偏移 `j ≡ -d (mod step)`，
   那一处的种子一定命中。反过来：错配/indel 把完全匹配切成的每一段都比 `step` 短时，
   可能漏掉这个种子。本线目标是细菌重测序（与参考差异 <1‰、读长 100~150 bp），
   连续完全匹配段远长于 4，所以 `step=4` 在目标数据上是安全的。

4. **重复 k-mer 整条剔除，不是截断保留前几个**。只留前几个位置的位置表"看起来能用、
   其实有系统性偏差"——它永远偏向参考上靠前的拷贝。剔除条数计在
   `SeedIndex.pruned_kmers` 里随统计报出来，便于解释"某块区域覆盖度为什么异常"。

5. **比对内部的取舍是"打分"而不是"最小编辑距离"**：匹配 ``+1``、错配 ``-1``、
   **每个 indel ``-3``**、**软剪裁 0**（两端各受 `max_clip` 限制）。空位罚得比错配重，
   是因为 indel 在真实数据里比替换罕见得多——两边同罚时，DP 会用"错配 + 空位"拼出一个
   分数略高的**假 indel**（这个坑是测试抓出来的，见设计记录）。报告里给出的仍是编辑距离
   （错配 + indel 碱基），挑候选对角线时也按编辑距离排序。并列时按两条写死的规则取舍：
   **格内**优先走对角（匹配/错配），其次插入，最后缺失；**终点**取剪裁更少的、
   再取更靠左的列。两条都有测试。

6. **read 两端可以不属于这段参考**：`max_clip` 允许两侧各剪掉若干碱基（``S``），
   因此 ``query_length`` 是整条读长，而 ``aligned_length = query_length - soft_clipped``
   才是真正参与比对的部分——**一致度的分母用的是后者**。跨参考末端（含环状原点跨越）
   仍然不处理。

7. **写出 SAM 的三条规矩**（`sam_output.py`）：负链记录的 ``SEQ`` 存**与参考同向**的
   反向互补序列、``QUAL`` 随之**反向**；坐标换成 **1-based**（``POS = 起点 + 1``）；
   **只写比对上的记录**（与 bowtie2 默认一致，上游 breseq 也把未比对的另存为
   ``*.unmatched.fastq``）。随记录写 ``NM``（编辑距离）与 ``MD``（错配位置串，
   ``^`` 接被删的参考碱基；插入与剪裁不进 ``MD``）。

8. **映射质量是"粗粒度的唯一性信号"**，不是 bowtie2 的 MAPQ 标度：
   短名单里只有一条可行候选 → **60**（唯一）；另有候选且**编辑距离相同** → **0**
   （无法区分）；另有候选但明显更差 → **20**。`Alignment.is_unique` 等价于 `mapq == 60`。
   下游（breseq 式的证据模型）不依赖这个数值，它主要给外部工具与人工查看用；
   将来若要按唯一性过滤，这里的粒度要再细化（记在待办）。

**同一份输入两次跑的结果完全一致**：先比编辑距离（少者优），再比种子票数（多者优），
最后按（起点、参考名、链方向）定序——不依赖字典遍历顺序；DP 内部的两条并列规则也是写死的。

- **索引**守两条：**位置真**（每条 k-mer 的每个位置回切参考、编码必须相等）与**位置全**
  （把参考上所有 `≡ 0 (mod step)` 的窗口独立算一遍，与索引逐条相等；多一个、少一个、
  被截断都会被发现——专打"重复 k-mer 只留前几个"那类写法）。
- **带状局部比对**的期望值全部能手算，所以写死 CIGAR 与各项条数：完全匹配、中间错配、
  参考多碱基（D）、read 多碱基（I）、参考两端自由、超出带宽返回"不可达"、窗口偏移加回
  绝对坐标、**并列时的确定性**，以及结果自身的一致性校验（CIGAR 消费的 query / 参考长度
  必须与声明一致）。**末端处理**单独一组：外来前缀被剪成 ``S`` 且参考起点跟着推进、
  剪裁上限与最短参与长度各自生效、**内部错配不会被剪**、默认 `max_clip=0` 时不剪。
- **比对器**守**真值对拍**：从已知参考"切"出 reads（位置、链方向、错配数已知）逐条核对。
  覆盖正负链、0~6 个错配、含 N、过短读段、参考两端、重复区（候选数 ≥ 2）、
  **跨链择优**（正向 3 错配 vs 负向 0 错配时选负向）、末端读通、**indel 三种情形**
  （read 多一个碱基 → I；少一个碱基 → D；缺口正好在 read 开头 → 只是起点后移）、
  超过带宽的 indel 被拒、确定性、参数校验。**映射质量**三条：唯一命中给 60、两处一样好给 0、
  另有一处更差给 20。真实数据那组在 **phiX174 真实参考**上模拟 200 条 read
  （正负链各半、错配 0~2），要求**全部**被找回且起点与链方向完全正确。
- **SAM 输出**两组：① MD 串与记录转换的能手算用例（一个错配、一个缺失、剪裁 + 插入、
  正负链的 ``SEQ``/``QUAL`` 朝向、无质量串写 ``*``、双端标记）；② **端到端**——
  在 phiX174 上造三类 read（正向、负向带 1 错配、接头读通），比对 → 写 SAM →
  **再用公共层的读取器读回来**逐条核对坐标、链方向、CIGAR、``NM``、``MD``、剪裁。
  走一遍公共层契约，等于顺带验了"写出来的东西别人读得懂"。
- **分片 F 对拍**（`tests/test_mapper_accuracy.py`，6 项）用**默认参数**在合成参考上查整体表现：
  ① 362 条混合 read（精确、1~4 个替换、1~2 个插入/缺失、替换与 indel 混搭、首尾读通、
  含 N、参考两端、越界应拒、随机外来）——可映射的 322 条**全部找回且逐项吻合**，
  越界的与外来的一条都没比上（**0 误报**）；② 每条比对都用 CIGAR 独立重放一遍，
  核对错配/插入/缺失/剪裁四项计数与 CIGAR 自洽；③ 无缺口全匹配的 read 另用 `str.find`
  数一遍逐字出现次数，出现多次时不许声称唯一；④ **MAPQ 校准**：唯一区 / 完全重复区 /
  近重复副本三组，用**独立于 mapper 的暴力扫描**（逐窗口数错配、正反两链）复核"唯一"这个
  断言；⑤ 20 个等好拷贝时必须是 0；⑥ 稀疏索引的代价：完全匹配段压到比 step 短时，
  step=64 漏 16/30、step=1 一条不漏。另外放量写一遍 SAM 再读回来，用 CIGAR + 参考
  **独立重算 NM / MD** 逐条核对坐标、朝向与标签。

> 写这些用例时踩到的坑值得记下：**拿重复度高的序列去测 indel，会得到"记成错配"与
> "记成空位"代价相同的并列情形**，那时测的就不是 indel 本身了。所以 indel 用例一律用
> 固定种子的随机序列，并且只对"代价唯一"的情形断言具体 CIGAR；并列情形只断言代价、
> 覆盖范围与确定性（不假装只有一种正确写法）。

## 附：设计记录

### 选择依据

**为什么自研、以及目标是什么。** breseq 的入口是 bowtie2，而 bowtie2 没有 Windows 构建
（上游只支持 Unix-like）。自研的目标不是复刻 bowtie2 的比对选择，而是给出
**足够好且行为可解释**的比对，让下游变异调用能在合理容差内复现上游结论——
验收口径是"比突变集合"，不是逐位一致（见算法清单 5.5.3）。

**为什么从种子-扩展起步，而不是 FM-index / BWT。** 目标数据是细菌级参考（几 Mbp）
加 1‰ 差异的短读。种子-扩展在这个区间足够灵敏，实现与验证都直观（每一步都能用
"位置是不是真的"这类性质断言）；FM-index 更省内存、查询更快，但实现复杂度与出错面
都大得多，收益主要在"参考很大"或"需要精确后缀查询"时。先用简单结构把**行为**做对、
把与上游的差异说清楚，再按实测决定要不要换。

**为什么参考只建正链索引。** 负链 read 靠查反向互补 k-mer 落到同一份索引上，
建两份只是内存翻倍，没有换来任何信息。正负两个方向在**同一个循环里收集候选**，
因为"挑最好的一条"必须把两个方向放在一起比。

**为什么错配上限是 4 而不是更紧。** 真实的变异位点在 read 上就是错配。上限太紧会把
"携带真变异的那些 read"连同比对一起丢掉，下游的变异调用就看不到证据了。
所以这个上限的作用是**排除明显不合理的比对**，不是"追求干净"。

**为什么软剪裁必须参与打分（走过一次弯路）。** 分片 D 我最初写成"先按编辑距离选最优路径、
再把两端异常碱基剪掉"，测试立刻抓出真问题：DP 会选一条"把这些碱基吸收成错配"的等价路径
（代价相同），剪裁根本改不动它——接头读通的 read 于是得到**起点偏了几位、还带假 indel**
的结果。改成打分制（匹配 +1、错配 −1、indel −3、剪裁 0）后，剪裁才真正参与"怎么对齐"这个
决定，同一份输入给出的是"8S + 100M、起点回到真来源"。**教训**：如果一个处理步骤要影响
结果，它就必须进入目标函数，不能做成事后的修补。

**为什么空位罚得比错配重（第二次弯路，同一个测试抓出来的）。** 分片 E 关掉剪裁做对照时，
那条接头读通的 read 被解释成"``4S4M1D100M``"：它多覆盖了 4 个参考碱基、付一个缺失，
却换来 103 个匹配，总分 101 反超正确答案的 100 分。错配与空位同罚时，DP 就会这样**拼出
假 indel**。indel 在真实数据里比替换罕见得多，把空位改成 ``-3`` 之后：真实的缺失省下的
错配远多于 3 分、照赢不误，而拼出来的假 indel 赢不了了。**教训**：打分要反映"哪类事件更
常见"，不只是"哪个更省"。

### 分片 F：端到端对拍与性能实测

**对拍怎么做的。** 参考用固定种子随机生成（真值必须完全掌握在自己手里），reads 从参考上
"切"出来再按真值施加变异，因此位置、链方向、错配/插入/缺失数、剪裁数全部是先验已知的，
可以逐条断言而不是"看着差不多"。口径沿用 `test_mapper.py` 立下的两条纪律：替换一律换成
**不同**的碱基（否则"换成同一个碱基"会让实际错配数小于预期，测试变成假通过）；
末端读通的外来碱基**逐个挑成与紧邻参考位不同**（否则 DP 会合理地"多对齐一位、少剪一个
碱基"——那是并列时取剪裁更少的正常取舍，真值就不唯一了）。

**结果（默认参数，参考 20 kb，362 条 read）：**

| 项 | 结果 |
| --- | --- |
| 可映射 read | 322 条，**全部找回**；起点、链方向、错配/插入/缺失/剪裁数逐项吻合 |
| 越界/外来 read | 40 条（错配 5 个、插入 4 碱基、随机外来），**一条都没误比上** |
| CIGAR 自洽 | 每条比对结果都按 CIGAR 独立重放一遍，四项计数与 CIGAR 完全自洽 |
| MAPQ 唯一性 | 唯一区给 60（暴力扫描确认全参考仅一个完全匹配）；完全重复区给 0；近重复副本挑中真正匹配的那一份；20 个等好拷贝给 0 |
| 稀疏索引代价 | 完全匹配段压到比 step 短时：step=1/4/8/16/32 一条不漏，step=64 漏 16/30 |

**性能实测（`tools/benchmark.py`，Python 单线程）：**

```bash
python modules/bio_analysis_function/submodules/read_mapping/tools/benchmark.py --reference-size 500000 --reads 1000 --step 1
```

| 场景 | k / step | 窗口数 | 建索引 | 索引内存（保留） | 建表峰值 | 比对 |
| --- | --- | --- | --- | --- | --- | --- |
| 1.0 Mbp 参考 | 16 / 4 | 249,997 | 0.38 s | 38.6 MB（162 B/窗口） | 65.8 MB | 0.91 ms/条、~1,100 reads/s |
| 4.6 Mbp 参考 | 16 / 4 | 1,149,997 | 2.02 s | 171.6 MB（156 B/窗口） | 286.2 MB | 0.95 ms/条、~1,050 reads/s |
| 0.5 Mbp 参考 | 16 / 1 | 499,985 | 0.84 s | 77.2 MB（162 B/窗口） | 130.2 MB | 0.95 ms/条、~1,050 reads/s |

三点结论：

1. **耗时与内存分开量**。`tracemalloc` 开着会让执行慢好几倍，混在一起量出来的耗时不可用；
   所以脚本先不带跟踪跑一遍量时间，再开跟踪跑一遍量内存（并断言两遍结果完全相同）。
   早先 v0.34 记录的"4.6 Mbp 建索引 8.39 s / 300 MB"就是把跟踪开着量的——窗口数
   （1,149,997）与现在一致，差的只是那层跟踪开销。
2. **内存由窗口数决定，约 155~160 字节/窗口**（保留部分）。所以稀疏（`step=4`）不是可有可无
   的优化：4.6 Mbp 逐位建按此外推约 700 MB（外推值，未实测）。
3. **比对速率约 1,000 reads/s、每条约 1 ms**（150 bp）。按 5M 对 read 的细菌重测序折算，
   单线程约需 2.8 小时——**Python 只适合小规模验证**，真实数据必须进原生层；
   原生用 2-bit 打包 + 有序数组，同量级参考的索引可压到十几 MB。

**与上游对拍的边界（说清楚，不含糊）。** 分片 F 的验收里写的"与上游 SAM 的下游一致性"
**只做成了一半**：本机环境里没有 bowtie2 / samtools / breseq / bwa / minimap2，也没有 IGV，
因此**没有**做"拿 bowtie2 的 SAM 喂进同一套下游做阶段级对拍"这件事。做成的那一半是：
把自己的 SAM 放量写出、用公共层读回来，再用 CIGAR + 参考**独立重算** `NM` 与 `MD` 逐条
核对——对出契约（坐标 1-based、负链存反向互补、`NM`/`MD` 语义）由这条测试守住，
但**它不等于外部工具互操作验收**。真正的阶段级对拍要等能装上游工具的环境（第 5.5.3 条
决策里的"接受外部 SAM/BAM"就是为它准备的入口）。

### 已知限制与待办

- **indel 只到带宽为止**：默认 `max_indel=3`，超出带宽的插入/缺失找不到比对（有测试）。
  长 indel 需要更宽的带（代价是 O(读长 × 带宽)），或者换成仿射空位罚分——都记在待办里。
- **软剪裁每端最多 10 个碱基**（`max_clip`）。接头读通比这更长时，超出的部分仍会被吸收成
  错配/插入（或整条比不上）。真实数据里接头读通常在 read 末端几十个碱基，这个上限迟早要
  按实际情况调——但它同时是"防止在无关序列上剪出一段短匹配"的护栏，所以不设成无限大。
- **环状参考的原点跨越不处理**：read 必须完整落在参考范围内，跨末端的比对一律不接受。
  GenBank 里跨原点的**特征**用 `join` 表达（那是 `reference_io` 的事），但**read** 跨
  原点需要一套回绕语义，目前没做。
- **映射质量是粗粒度的**（三档 60 / 20 / 0，见第 4 节第 8 条），不是 bowtie2 的标度。
  重复区里挑哪一条目前是"编辑距离相同时取更靠左的"——对变异调用够用（重复区的证据本来
  就要单独处理），但要按唯一性做过滤时，这里的粒度得细化。**"唯一"的判定范围**是进入
  短名单并通过过滤的候选；分片 F 用独立暴力扫描在合成重复/近重复数据上**没有测到反例**，
  但那不等于证明了全参考范围的严格唯一性——候选被 `max_candidates` 截断时理论上仍可能
  过于自信，这条留给"要按唯一性过滤"的那一步去收紧。
- **高拷贝重复区里的 read 会整条丢**（分片 F 实测钉住）：区内 k-mer 的位置数超过
  `max_hits=64` 就被整条剔除，read 于是拿不到任何种子。这是"宁可漏、不可偏向某个拷贝"
  的代价——真实基因组里的 rRNA 操纵子等高拷贝区需要更高拷贝数的数据来评估影响，
  目前只有合成数据上的一条测试守着这个行为。
- **未提供线程参数**：当前是 Python 单线程实现。按本项目节奏，等进原生层时再谈并行，
  现在暴露一个不生效的参数只会误导。
- **原生移植未做**（见上文实测：约 155 字节/窗口、1 ms/条，真实数据量级下必须进原生层）。
- **算法广场入口已登记契约**（`bio-read-mapping`，分类「参考比对」，`beta`），
  但**执行链路未接通**——界面会照实提示"只登记调用契约，提交会被拒绝"。
  要接通还需两步：给比对器加一个 JSON 入口（照 `modules/workflow` 的 `wrapper.py` 那样
  收 JSON、吐 JSON），再在 Electron 侧登记；这两步属于后续任务，不在本分片内。
- **与上游工具的互操作验收未做**（分片 F 已如实记）：本机没有 bowtie2 / samtools / IGV /
  breseq，所以只做了"自家 SAM 写出 → 读回 → 独立重算 `NM`/`MD`"的自洽核对。
  真正的阶段级对拍要等能装上游工具的环境。
