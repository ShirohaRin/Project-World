# 原生加速层：C++ 算法核心与 C ABI

> 本文件由《生物方法模块算法清单》5.4.0 节拆出；子节编号沿用原文档，便于与历史记录对照。


> 编号说明：$5.4.0$ 不是算法，而是**这条预处理线所有算法共用的实现层**。
> 它给 $5.4.1$ 起的每个算法提供高速的读写与逐碱基计算能力，因此排在算法之前。

### 5.4.0.1 为什么这条线要有一层原生实现

纯 Python 跑不动测序数据的规模。质量剪切在 100 万条 151bp 的合成数据上实测：
Python 实现 **12.26 s**，原生实现 **0.66 s**（$18.5\times$）。一个真实样本常在
千万到亿级 read，这个差距会变成"能不能当天出结果"的差别。

因此这条线采用分工而非替换：**Python 负责接口、编排与数据结构，C++ 负责逐碱基扫描**。
这不是"顺手优化"，而是这条线的既定工程约束——它决定了每个算法的交付形态。

### 5.4.0.2 分层与语言边界

```text
IDEA Assistant 产品层（生物计算方法广场）
        ↓
Python 算法层（submodules/<算法>/）
        ↓  ctypes
C ABI（include/bio_native.h）
        ↓
C++ 算法核心（src/*.cpp）
        ↓
FASTQ / gzip 数据
```

**为什么是 C ABI，而不是 pybind11**：C 接口只用基本类型与结构体指针，因此编出来的
共享库与 Python 版本、编译器厂商都无关（本项目的库由 MinGW 编出，官方版 Python
是 MSVC 编译的，照样加载）；语言边界也因此可替换——将来若要把核心换成 Rust
或更快的 C++，只要仍导出这组函数，Python 侧一行都不用改。两侧要交换的只是
"文件路径 + 几个参数 + 统计数字"，不需要对象级转换。

**位置：模块公共层下，`modules/bio_analysis_function/common/native/`。**
它和 `common/fastq.py`、`common/io.py` 同级——都是与具体算法无关的公共能力，
只是这一层用 C++ 写。放在 `common/` 之下是为了让"它不是算法"这件事一眼可见：
`submodules/` 下才是算法。公共层每一件工具的**产出**逐条写在
[common/README.md](../README.md) 里（含它给谁用）。

两处命名与内容的取舍值得记一笔，都是**踩到之后才明白**的：

- **构建脚本目录叫** **`tools`、脚本叫** **`compile.py`，不叫** **`build`**。仓库根
  `.gitignore` 有 `build*` 规则（本意是拦前端构建产物），它不只拦 `build/` 目录，
  也拦 `build.py` 这种**文件名**——第一版就叫 `native/build/build.py`，
  `git status` 里那个目录一直是"未跟踪"，构建脚本根本进不了版本库。
  处理方式是让名字避开规则（目录 `tools/` + 文件 `compile.py`），
  而不是去改那条全局规则。
- **zlib 只留编译所需文件**。上游整棵树（`contrib/`、各平台工程、示例、文档）
  与本项目无关，看着还像"往仓库里塞了一次克隆"；精简后只剩 12 个 `.c`、
  10 个头文件与 LICENSE/README，来源与许可证保留在原处。

### 5.4.0.3 C ABI 契约

- **状态码** `bio_status_t`：`BIO_OK` 与五类失败（输入不存在 / 输入格式 / 输出 /
  参数 / 内部错误）。用枚举而不是 `errno`，因为 `Python` 侧需要据此区分
  "用户传错了参数"与"数据有问题"，处置方式不同。
- **统计结构** `bio_stats_t`：`total_reads / kept_reads / changed_reads / dropped_reads /
  bases_before / bases_after`，字段与口径和 Python 侧 `FastqStreamSummary` **完全一致**，
  因此两侧的统计可以直接比较（测试就是这么用的）。
- **结果结构** `bio_result_t`：固定大小、调用方分配、被调方填充，不涉及内存所有权
  转移，因此不存在跨语言释放问题；失败原因写入固定长度的 `message`。
- **过滤结果另有一个结构** `bio_filter_result_t`：在通用统计之外多一块
  `bio_filter_breakdown_t`（按原因分类的失败条数）。**没有去改** **`bio_result_t`**
  ——那个布局已经被两个算法用着，为一个新算法改共享结构的布局，代价与风险都不值。
  相应地，`set_failure` / `translate_exception` / `prepare_result` 在这一版做成了
  模板：两种结果结构的前两个字段同名同型，状态与消息的写法收在一处，
  免得两套措辞各自漂移。
- **比例类参数用万分之一整数**（basis point），不用浮点：C ABI 里出现浮点字段时，
  结构体布局依赖编译器的对齐规则，整数没有这个隐患；4 位小数足以无损表示实际会设的
  阈值（40% → 4000，30% → 3000），算法内部再还原成与 Python 版**同序**的浮点运算，
  因此边界比较的结果逐位一致（这一条由对拍测试守着）。
- **结果码照抄上游数值**：`bio_filter_verdict_t` 与 fastp `src/common.h` 同值
  （0/12/16/17/20/24），Python 侧的常量也是同一套数字，因此两侧的失败分类字典
  可以直接比较——对拍测试就是这么做的。
- **第二输出路径是独立参数，不放选项结构里**：reads 过滤的 `failed_out`（被丢弃
  read 的归档）与选项结构分开传——选项结构装的是**算法语义**（阈值、开关），路径
  属于 I/O，放进去了就让"字段与 Python 侧 `ReadFilterConfig` 一一对应"这句话失效。
  `NULL` 与空串都表示"不产出这份归档"。归档内容与上游 `--failed_out` 同口径：
  原始记录 + 名字后追加原因标签，标签表在 `pipeline.h` 的 `verdict_label`。
- **字符串**：一律 UTF-8、以 NUL 结尾。
- **线程数**：参数里的 `threads` 只影响速度，**不影响结果**——输出文件逐字节相同、
  统计完全相同（有常驻测试守着）。`<= 0` 由实现自行决定，**取哪一个按算法各自的实测来定**
  （质量剪切 / poly 修剪 / 接头裁剪取单线程，reads 过滤取硬件并发，理由见 $5.4.0.5$；
  双端合并与双端按 overlap 裁接头取硬件并发，但这两条**尚未做基准**），
  `1` 也是单线程，`> 1` 显式启用流水线。
  **唯一没有 `threads` 参数的是去重**：它的判定依赖全部历史 read，只能串行执行，
  给一个"能调但调了没用"的参数反而误导（见 $5.4.0.5.2$）。
- **统计用的是不透明累加器，而不是"一次调用填结构体"**。原因在产物形态：
  其他算法的产物是"文件 + 几个数字"，本算法的产物是一份**报告**——11 条与读长
  同长的曲线、1024 个 5-mer 桶、94 项质量直方图、读长分布。它们的**长度在运行期
  才知道**（取决于数据的最长读长），塞不进定长结构体，也不该让调用方去猜容量。
  于是改成 `bio_stats_create` → `bio_stats_scan_fastq`（可多次，把多份文件累加）
  → 按需查询 → `bio_stats_destroy`。句柄由创建方销毁，跨 ABI 不转移所有权、
  不暴露内部布局；查询函数在容量不够时返回 `BIO_ERR_OUTPUT` 并回填所需长度。
- **质量分布对外报 Phred、对内按字符码存**。内部沿用上游的"按质量字符码
  （0~127）下标"，但 C ABI 的 `bio_stats_quality_histogram` 输出的是 **Phred 值
  （0~93）下标**——字符码是 Phred+33 的表示细节，不该泄漏给调用方。
  对拍测试第一次就跑出了两侧键整整差 33，正是这一处。
- **第四种结果形态：不透明句柄承载整条流程的结果**。到工作流为止，本层的结果形态
  共四种：① 一次调用填**定长结构体**（`bio_result_t` / `bio_filter_result_t`）；
  ② **不透明累加器**——长度运行期才知道，先 create、可多次扫描、按需查询、
  创建方销毁（`bio_stats_handle`）；③ 定长结构体 + **调用方分配的变长数组**
  （插入片段直方图，容量不够时回填所需长度）；④ `bio_workflow_result_t`。
  第四种的独特点是**结果内部还挂着子句柄**：工作流把四个质量统计直接写进句柄内联的
  `bio_stats_handle` 里，`bio_workflow_stats` 返回的是**借用**指针——调用方按槽位取用，
  **不要单独销毁**，它们随结果一同销毁（见 `workflow.h` 的 `WorkflowStatsSink`）。
  这样既不必在跑完之后把曲线再复制一份，也不必让工作流知道"句柄"这种东西。
- **子结构体全零视为"没给"，回退到该算法的默认值**。这是工作流参数
  （`bio_workflow_options_t`）里的一条专门约定：C 调用方习惯 `memset` 清零，而各子结构体的
  默认值**不是零**（质量窗口 4、poly 最短 10、过滤阈值 15/40/5、overlap 的 5/30/2000……）。
  不这么处理的话，"清零之后静默换了一套参数"就是个很难发现的坑。实现里用一个
  `bytes_are_all_zero` 判断把全零的子结构体换成 `NULL`，交给那个算法的默认值构造去填。

### 5.4.0.4 gzip：为什么用 zlib 的 gzFile

上游 FASTQ 几乎总是 gzip，因此读入要能解压、输出要能压缩，而且**必须是流式的**
（几十 GB 的文件不能整体进内存）。最终选择 zlib 的 `gzFile` 接口：

- `gzopen` / `gzread` **自动识别并按需解压**，未压缩文件也能直接读，上层不必分支；
- 它自动处理**多 member** gzip（pigz、bgzip 等工具的常见输出形式）；
- 它是真正的流式接口，内存占用与文件大小无关。

最初考虑过 libdeflate（更快），但它的解压接口要求输入缓冲里至少包含一个**完整的
gzip 成员**，而常见的 `.gz` 是单成员——那等于要求整个文件进内存，因此放弃。

压缩策略是三态的：**显式指定优先，否则跟随输入**；判断输入是否 gzip 看的是
**魔数而不是扩展名**（`.fastq` 被外部工具压成 gzip 后不改名也能正确处理），
输出同样不看输出文件名的扩展名。写出模式为 `"wb6"`（gzip）与 `"wbT"`（zlib 的
透明写模式，即不压缩）。

### 5.4.0.5 多线程流水线

单线程时三件事被迫排队：**读一块（含解压）→ 算一块 → 写一块（含压缩）**。
流水线把它们拆到不同线程上重叠执行：

```text
┌──────────┐        ┌────────────┐        ┌──────────┐
│ reader   │──批次──▶│ worker × N │──批次──▶│ writer   │
│ 1 个线程 │        │ 线程池      │        │ 1 个线程 │
└──────────┘        └────────────┘        └──────────┘
     ▲                                           │
     └────────── 反压：未写出批次数有上限 ◀─────────┘
```

三条纪律保证"多线程与单线程输出逐字节一致"：

1. **按批次传递**。worker 处理的最小单位是一批 read（1024 条），批次下标单调，
   writer 严格按 0、1、2…… 写出，因此输出顺序永远等于输入顺序，与调度无关。
2. **槽位环**。批次放在固定数量的槽里（槽数 = worker 数 + 2），槽只有
   `Free → Filled → Computed → Free` 三种状态，任何时刻只有一个线程持有某个槽，
   不需要锁住整条流水线。
3. **有界在途**。未写出的批次数有上限，内存占用因此有上界，与输入大小无关。

**失败归档复用同一条流水线。** `run_pipeline` 有一个可选的 `dropped_path`：非空时，
worker 把被判丢弃的 read（序列与质量原样，名字后追加原因标签）收进本批次的槽里，
writer 在写出主输出之后**按同一批次顺序**把它写进归档。收集发生在"每个批次只有
一个线程在写"的位置，写出发生在已经保序的 writer 线程，因此不新增同步点、
不需要额外线程，归档同样满足"多线程与单线程逐字节一致"与内存有界这两条。
中途失败时主输出与归档**两份半成品都删**。

任一线程抛异常都会立刻置 `aborted` 并唤醒所有等待者，各线程在最近的检查点退出，
异常被捕获到 `error` 中，**等所有线程 join 之后再原样抛出**——调用方看到的错误
与单线程完全一样，且半成品输出仍会被删除。（写出阶段的异常必须就地收住：
此时其它线程还在跑，异常若提前离开函数，`std::thread` 析构会因为线程仍 joinable
而直接终止整个进程。）

**实测结论：当前两个算法上多线程没有收益。** 100 万条 151bp：

| 场景           |  Python |       原生单线程 | 原生 16 线程 |
| ------------ | ------: | ----------: | -------: |
| 未压缩 301.3 MB | 12.26 s |  **0.66 s** |   0.79 s |
| gzip 49.3 MB | 69.28 s | **17.91 s** |  19.10 s |

原因是这个负载**不是 CPU 密集**：单线程已经跑到约 900 MB/s 的读写吞吐，瓶颈在
磁盘与 gzip 编解码（zlib 的 inflate / deflate 都在单线程里做，加 worker 也帮不上），
而多线程额外带来了跨核的数据搬运与同步开销，因此反而慢 19%。

> gzip 那一行的 Python 基线用的是 Python `gzip` 模块的默认压缩级别 9，而原生侧
> 固定用 zlib 级别 6，因此那里约 $3.9\times$ 的差距里含一部分压缩级别差异，
> 不能全部记在"实现速度"头上；未压缩那一行不存在这个干扰。

据此，质量剪切与 poly 修剪的**默认线程数取 1**（`threads <= 0` 走单线程直路）。
这条结论也解释了为什么"移植到 C++"的收益远大于"在 C++ 里加线程"。

**但默认值不能一刀切——reads 过滤就是反例。** 它逐条要跑四类判据（还可能加一次
复杂度扫描），计算占比明显更高。30 万条 151bp（未压缩 90.3 MB）实测：

| 实现      |                        耗时 |
| ------- | ------------------------: |
| Python  |                    4.73 s |
| 原生 1 线程 |                    240 ms |
| 原生 2 线程 |                    169 ms |
| 原生 4 线程 |                    132 ms |
| 原生 8 线程 | **122 ms**（约 $2.0\times$） |

因此 `threads <= 0`（自动）的含义改成**按算法各自的实测来定**：质量剪切与 poly 修剪
取单线程，reads 过滤取硬件并发数（流水线里由 `AutoThreads` 表示，调用方在 C ABI 层
给出）。两个取值都不影响结果，只影响速度。

同一批数据走 gzip（15.0 MB）时，1/2/4/8 线程分别是 6.65 / 6.40 / 6.41 / 6.51 s——
基本不变。这里真正的瓶颈是**写出端的单线程 deflate**（90 MB 数据压回去要几秒），
加 worker 帮不上忙。这正好说明 $5.4.0.9$ 那条待办的价值：要让 gzip 路径快起来，
该并行化的是压缩本身（多 member 输出），不是计算。

### 5.4.0.5.1 双端数据的另一条流水线

单端那条一次只喂一条 read，装不下"必须成对处理"的算法。三个双端算法（双端合并、
双端按 overlap 裁接头、双端重叠区碱基校正）走的是 `paired_pipeline.h`：**同步读 R1 与
R2**、每步拿到一对 read、按批次保序把结果交给写出方。三条纪律（按批次传递 / 槽位环 /
有界在途）与单端完全一致，批量大小与线程数也共用同一套（`kBatchRecords` 与
`resolve_threads`），口径不会漂移。

它与单端流水线有两点结构差异，都是"成对"带来的：

1. **配对完整性由流水线保证**：一端先读完而另一端还有记录时**直接抛格式错误**
   （配对关系已经破坏），不会静默丢弃多余的那些 read 或把它们配上错误的伴侣。
2. **结果类型由算法决定**：流水线不规定 worker 返回什么，只负责把它从 worker 搬到
   写出方。因此"裁接头要写两个文件、合并只写一个"这类差异都留在算法自己的回调里。

> 这条流水线原先长在合并算法内部（当时它只有一个使用方）。按 `开发规则.md` 3.2 的
> "公共能力至少出现两个真实使用方之后再提取"，它在第二个双端算法落地时上移到这里。

### 5.4.0.5.2 去重是唯一**不走流水线**的算法

重复检测（`src/dedup.cpp`）用的是布隆过滤器，判定**依赖此前处理过的所有 read**——
位图是跨 read 累积的共享状态，谁先被处理，谁就"不重复"。把这种有状态判定放进
worker 池，结果会随线程调度漂移，直接违背"多线程与单线程逐字节一致"这条纪律。

因此它的实现**固定为单线程串行**：读（含解压）→ 判重 → 写（含压缩）依次执行，
C ABI 里也**没有 `threads` 参数**（别的算法都有）。这不是偷懒，而是算法性质决定的：
它的重复率是数据的**确定函数**，同一份输入任何时候跑都一样。

> 与上游的差别要如实说明：fastp 在 worker 线程里调用 `Duplicate::checkPair`，
> 所以**同一份数据换线程数，它报出的重复率会变**（谁先谁后不同，被判为重复的
> 那一条就不同）。本实现不会。这是刻意选择的确定性，不是实现差异。

能并行的部分（读取端解压与写出端的压缩/判定重叠执行、或"worker 并行算位置向量 +
writer 保序做位图 OR"）留给后续优化。当前版本先把口径做对——位置向量是纯函数，
位图操作必须串行，这条边界在代码里写得很清楚（`accumulate` 与 `apply_bitmap` 分开）。

### 5.4.0.5.3 工作流为什么自带一条流水线

工作流（`workflow_pipeline.h`）没有复用 `pipeline.h` 与 `paired_pipeline.h`，
而是自己实现了一条。三条流水线的**设计纪律完全相同**（按批次传递、槽位环、有界在途，
见 $5.4.0.5$），差别只在"流水线两端允许做什么"——而工作流对两端的要求，前两条都满足不了：

| 流水线 | 读取端 | 写出端 |
| --- | --- | --- |
| `pipeline.h` | 不做事 | 固定写一个文件（可选再写一个失败输出） |
| `paired_pipeline.h` | 不做事 | 由算法自己决定 |
| `workflow_pipeline.h` | **有状态、顺序相关的判定**（去重、按 index 过滤、过滤前统计） | **多路分流**（主输出 / 落单 / 失败 / 合并 / 重叠区）+ 分卷 |

**读取端要有钩子**：去重的位图跨 read 累积、"谁先出现谁不算重复"，只能单线程按文件
顺序判；按 index 过滤与过滤前统计同样要在进批次之前完成（见 $5.4.0.5.2$ 与工作流的
`prepare`）。既有的两条流水线读取端不做事，装不下这些。**写出端要多路分流**：
`paired_pipeline.h` 只规定"结果由算法搬到写出方"，而工作流要同时维护五个输出
（外加分卷），写出逻辑比单条流水线的固定形态复杂得多。

不为这三条流水线抽公共骨架的理由很直接：前两条的契约已经稳定、各自有多个使用方与
常驻测试，为一个新使用方去参数化它们，改动面与风险都不划算。工作流复用它们的
**基础设施**（`pipeline_detail::kBatchRecords`、`resolve_threads`、`add_stats` 等），
只自己实现槽位环与保序消费。将来若出现第四条同类流水线，那时才是把骨架提取出来的时机。

> **这一轮顺带修掉一个既有缺陷：空输入会死锁。** 三条流水线的写出端等的都是**槽的**
> 条件变量；而读取端在**一个批次都没发出就收工**（输入为空、或 `max_records` 为 0 拦住）
> 时，原本只唤醒了 `work_cv`，且写出端的等待谓词里没有"读取端已收工"这一条——
> 于是通知到了、谓词看一眼又睡回去，写出端永远停在那里。修法是三处一起：收工时
> **唤醒所有槽**（`fail_slots`）、写出端**谓词加上"读取端已收工且这一批不存在"**、
> 并把 `reader_finished` 改成**原子量**（写出端要在不持锁时看它）。三条流水线
> （`pipeline.h`、`paired_pipeline.h`、`workflow_pipeline.h`）都受影响，都已修。

### 5.4.0.6 Windows 上的 UTF-8 路径（一个被基准暴露出来的真实缺陷）

在 Windows 上，zlib 的窄字符接口（`gzopen` / `fopen`）用**当前代码页**解释路径，
而本层对外收的是 UTF-8 字符串。中文系统上（代码页 GBK）两者不一致，后果不是报错，
而是"写成功"却生成一个名字乱码的文件，调用方在自己的输出路径上扑空——
基准脚本里带中文的场景名第一次就撞上了这个坑。

修复方式是统一的：路径先经 `std::filesystem::u8path` 转成宽字符，再走宽字符接口
（Windows 上 zlib 额外提供 `gzopen_w`；文件系统操作交给 `std::filesystem::path`）。
回归测试用中文目录 + 中文文件名（`测序数据/结果目录/样本1.fq` → `修剪后.fq.gz`）固定住。

### 5.4.0.7 构建与分发

```bash
python modules/bio_analysis_function/common/native/tools/compile.py
```

- **C 与 C++ 分开编译**：zlib 是 C89 代码，其中若干写法只在 C 下合法
  （`gzlib.c` 把 `void*` 隐式转成 `wchar_t*`，C++ 直接报错；还有 C++17 已废弃的
  `register`）。因此每个源文件各自编译成目标文件，最后统一链接。
- **静态链接 C++ 运行时**（`-static-libgcc -static-libstdc++`）：目标机器上没有
  装 MinGW，动态依赖会直接导致加载失败。
- 产物 `common/native/lib/bio_native.dll`（约 3.0 MB），随客户端一起分发；
  实测其依赖只有 `KERNEL32.dll` 与 UCRT 系列，**不额外引入任何运行时 DLL**
  （这一点在引入 `std::thread` 后专门确认过）。
- **当前库版本 0.17.0**（`src/api.cpp` 的 `kNativeVersion`），由 `bio_native_version`
  导出，供 Python 侧在加载后校验、避免用到过期的库（测试里断言了具体版本号）。
