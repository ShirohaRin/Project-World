# adapter_detection：reads 接头检测（公共层工具）

从一份 FASTQ 里找出**接头序列**（adapter），只给出结论与依据，不改数据。
算法与 fastp 1.3.x 的 `Evaluator::evalAdapterAndReadNum` 逐位对齐。

**它是工具，不是算法入口**。按 `开发规则.md` 3.2 的第 2 类：它的产出是一条接头序列，
自身价值不大、注定要被下一步（接头裁剪）消费。因此它**在生物计算方法广场上没有独立
入口**，而是在接头裁剪里作为一个选项出现（"接头来源：自动检测 / 手动指定"）；
位置也从 `submodules/` 移到了 `common/`。

**产出**：一条接头序列 + 来源（命中内置已知接头表 / 从数据中拼出）+ 证据
（采样规模、种子 k-mer、出现次数、富集倍数）；没检出时给出原因。
**不写任何文件**，也不改动输入数据。只需要一份 FASTQ 本身就能运行——
不需要参考基因组、不需要注释文件、不需要数据库，也不需要先跑别的算法。

---

## 1. 它解决什么问题

### 接头是什么，为什么要先把它找出来

测序文库的每一个 DNA 片段两端都连着**接头**：一段人工设计、序列固定的寡核苷酸，
用来把片段固定在测序芯片上、也承载样本的 index。如果某个片段的插入片段（insert）
比测序读长还短，测序仪就会**一路读进接头**——read 的 3' 端于是带上一段固定的
接头序列。这种残留会带来两个麻烦：

- 比对软件会把接头序列按"基因组序列"去比，比到奇怪的位置；
- 组装与去重会被这些相同的尾巴干扰。

**要先"找出来"再"剪掉"，是因为接头序列取决于文库构建用的试剂盒**（TruSeq、
Small RNA、各种 PCR Primer……），不同数据的接头不一样，写死某一个就会剪错。
所以这一步的产物是**一条结论**：这份数据的接头长什么样。

### 怎么找：两段式

**第一段：查已知接头表。** 内置 234 条常见接头序列（来自上游 fastp 的表，
原表又汇总自公共接头集合）。对每条 read，在任意位置拿表里的接头去比，
**每 16 个碱基允许 1 个错配**（说明书级别的容错，测序错误不至于让匹配失败）。
命中率超过阈值（2%，或 0.5% 且错配很少）就用表里那条**完整**序列作为结论。

**第二段：从数据里从头找。** 表里没有的话，就靠数据本身：接头出现在不同位置
（插入片段长短不一），但接头开头那几个碱基会**大量重复出现**，形成远超背景的
富集。于是：先统计所有 read 的 10-mer（从第 20 个碱基起扫），挑出显著富集的
作为**锚点**；再围绕锚点向前、向后各延伸出一棵前缀树（"占优"的子节点要求
占比 ≥ 95%、节点计数 ≥ 50），拼出完整的接头序列。拼出来的序列还会回头和已知表
对一次——如果能对上，就返回表里那条完整序列。

> **第二段在样本充分时经常给不出结果，这是上游的真实行为，不是缺陷。**
> 两个原因：① 扫描时排除 read 末尾 1 个碱基（末位很吵），拼接结果因此**缺末尾**；
> ② 各条 read 的插入片段长短不一，前缀树在接头的 3' 端就会提前停住。
> 结果拼出来的序列**短于**已知表里的条目，吸附失败，于是返回"未检测到"。
> 样本很小时反而会返回一个种子 k-mer——那是退化结果（前缀树计数不足 50，
> 两条路径都是空的）。两种行为都用测试固定住了。

## 2. 它在产品里怎么被用到（**没有独立入口**）

按 `开发规则.md` 3.2 的第 2 类，本工具**不在算法广场上单独出现**：它的产出（一条接头
序列）自身价值不大，用户真正要的是"把接头剪掉"。因此它会在**接头裁剪**的入口里作为
一个选项出现——**接头来源：自动检测 / 手动指定**；自动检测时用的就是下面这些参数。

**参数**（届时作为接头裁剪表单里的选项字段展示）：

| 参数 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| reads 文件 | 文本 | 是 | — | 由接头裁剪的输入提供（FASTQ，可 gzip）。当前只处理单端数据。 |
| 采样 read 数上限 | 数字 | 否 | 262144 | 最多采样多少条 read（与下一个上限谁先到算谁）。 |
| 采样碱基数上限 | 数字 | 否 | 39583744 | 默认 = 151 × 采样条数上限。 |
| 最少样本量 | 数字 | 否 | 10000 | 少于它就不做检测（样本太小不可信）。 |
| 种子 k-mer 长度 | 数字 | 否 | 10 | 从头检测时用的 k-mer 长度（4~12）。 |
| 忽略末尾碱基数 | 数字 | 否 | 1 | 扫描时丢掉末尾几个碱基（末位噪声大）。 |

**产出**：检测到的接头序列（可能为空）、来源（命中内置已知接头表 / 从数据中拼出）、
采样统计，以及从头检测时的证据（种子 k-mer、出现次数、富集倍数）；未检测到时给出原因。

> 这一节的参数与产出也是给课题组讨论用的：检测本身不进广场，但它的结论会
> 出现在接头裁剪这一步里。

## 3. Python API 用法

### 文件进、结论出

```python
from modules.bio_analysis_function.common.adapter_detection import (
    detect_adapter_from_file,
)

result = detect_adapter_from_file("raw_R1.fastq.gz")

print(result.render())
# 采样 read 数：262144（39583744 个碱基）
# 检测到接头（命中已知接头表）：AGATCGGAAGAGCACACGTCTGAACTCCAGTCA

if result.detected:
    adapter = result.adapter      # 交给下游的接头裁剪步骤
```

**本算法不写任何文件**：它的产物是一条结论，供后面的接头裁剪使用。

### 序列级（自己控制采样）

```python
from modules.bio_analysis_function.common.adapter_detection import (
    AdapterDetectionConfig,
    detect_adapter,
    sample_sequences,
)

sequences = sample_sequences("raw_R1.fastq.gz")          # 只要碱基，流式采样
result = detect_adapter(sequences, AdapterDetectionConfig(min_reads=1000))
```

### 原生实现（跑真实数据用这个）

上面的 Python 实现同时是**逐位对拍的规格**；实际检测请用原生层——
这个算法的第一段成本正比于"表长 × read 数"，纯 Python 在默认配置下就不可用了。

```python
from modules.bio_analysis_function.common.native import adapter_detect_fastq

result = adapter_detect_fastq("raw_R1.fastq.gz")
print(result.adapter, result.source, result.detected)

# 也可以跳过已知接头表（只做从头检测），或传自己的候选表
result = adapter_detect_fastq("raw_R1.fastq.gz", adapters=())
```

参数名与 `AdapterDetectionConfig` 的字段一一对应。`adapters=None`（默认）用
公共层的内置接头表（`common/known_adapters.py`，234 条）；传 `()` 跳过第一段。
返回的 `NativeAdapterDetection` 字段与 `AdapterDetection` 对齐。

## 4. 参数

`AdapterDetectionConfig` 的字段（默认值与 fastp 一致）：

| 字段 | 默认 | fastp 对应物 | 说明 |
| --- | --- | --- | --- |
| `max_reads` | 262144 | `READ_LIMIT = 256*1024` | 采样条数上限 |
| `max_bases` | 151 × 262144 | `BASE_LIMIT` | 采样碱基数上限 |
| `min_reads` | 10000 | 硬编码 | 低于它不做检测 |
| `key_length` | 10 | 硬编码 | 种子 k-mer 长度（4~12） |
| `shift_tail` | 1 | `max(1, trim.tail1)` | 扫描/拼接时忽略末尾几个碱基 |
| `max_adapter_length` | 60 | 硬编码 | 返回序列的截断长度 |
| `adapters` | 内置 234 条 | `getKnownAdapter()` | 已知接头表；传 `()` 表示跳过第一段（只做从头检测） |

参数越界会在构造配置时报错。

## 5. 输出解读

`AdapterDetection` 的字段：

| 字段 | 含义 |
| --- | --- |
| `adapter` | 检测到的接头序列；`None` 表示没检测到 |
| `source` | `"known"`（命中已知表）/ `"kmer"`（从数据拼出）/ `None` |
| `sampled_reads` / `sampled_bases` | 实际采样的规模 |
| `reason` | 未检测到时的原因（样本不足 / 已知表未命中且无显著富集 k-mer） |
| `seed_sequence` / `seed_count` / `seed_fold` | 从头检测时的证据：种子、出现次数、富集倍数 |
| `detected` | 属性，等价于 `adapter is not None` |

**怎么判断结论可信**：看 `source`。`"known"` 是"数据里的接头与已知序列吻合"，
可信度最高；`"kmer"` 是拼出来的，**长度可能只有 10 个碱基**（样本小的时候），
拿去做裁剪会有风险——这时更稳妥的做法是结合已知接头表人工确认。

## 7. 验证

```bash
python -m pytest modules/bio_analysis_function/common/adapter_detection -q
```

测试 30 项（算法 20、文件级接口 8、真实数据 3），全部通过。重点守四类口径：

- **两段式的阈值**：已知表命中与不命中两侧（含 0.5% / 2% 两条判定线）、
  容错规则（每 16 个碱基允许 1 个错配）、并列时取字典序更小的那条；
- **第二段的两种结局**：样本充分时"未检测到"、样本很小时返回 10 个碱基的种子
  （都是上游的真实行为）；
- **k-mer 编解码**：滚动取值与"每窗口重算"在 200 组随机数据上完全一致、
  含 `N` 的窗口无有效编码；
- **采样与稳健性**：条数 / 碱基数上限、gzip 输入、中文路径、缺失文件、
  零长度 read（真实数据里就有）。

**真实数据**（`tests/data/fastp_R1.fq`，9 条记录）只用来验证**门槛与稳健性**：
样本远少于 1 万条时必须如实报"样本不足"，把门槛降到 9 条也不会凭空报出接头。

## 8. 已知限制

- **只处理单端 read**。双端数据靠 overlap 分析找接头（`--detect_adapter_for_pe`），
  属于后续算法。
- **第二段常常给不出结论**（原因见第 1 节），实际起作用的主要是第一段的已知接头表。
  想要确定的结果，最稳的做法是直接给定接头序列（上游的 `--adapter_sequence`，
  本实现对应 `adapters` 参数）。
- **纯 Python 版跑不动满量输入**：第一段成本 ≈ 表长 × read 长度 × read 数，
  234 条表 × 1 万条 read 就要几十秒到几分钟。实际检测走原生层
  （`common.native.adapter_detect_fastq`）。
- **原生版最坏情况 16.4 秒**：干净数据（没有接头）时第一段的剪枝永不生效，
  234 条表要扫满 10 万条 read；有接头时快得多（20% 密度下 71 毫秒）。
  想更快可以先缩小采样上限，或直接指定接头序列（跳过检测）。
- **已知接头表是快照**（`common/known_adapters.py`，取自上游 v1.3.7），
  表会随试剂盒更新，需要同步机制。
- **不做裁剪、不产出文件**：把接头从 read 上剪掉是下一个算法（接头裁剪）。
- **实际计算执行链路尚未接通**，广场入口只到契约层。

#### 5.4.4.3 问题定义与算法原理

**接头为什么会长在 read 上。** 文库里的每个片段两端都连着接头（用来固定到测序芯片、
承载 index）。当插入片段比读长还短时，测序仪就会一路读进接头，于是 read 的 3' 端
带上一段固定序列。不同 read 的插入片段长度不同，因此接头出现在 read 里的**位置不同**。

**第一段：查已知接头表。** 对每条 read、每个起点，拿表里接头的前
$\min(\text{剩余长度}, \text{接头长度})$ 个碱基去比，允许的错配数是
$\lfloor \text{比对长度}/16 \rfloor$；任意一个起点过关就算这条 read 命中该接头。
命中率满足下面任一条就用表里那条**完整**序列作为结论：

$$
\text{maxCount} > \frac{\text{checkedReads}}{50}
\quad\text{或}\quad
\left(\text{maxCount} > \frac{\text{checkedReads}}{200}
\ \text{且}\ \text{mismatches} < \text{checkedReads}\right)
$$

（两处除法都是**整数**除法，上游如此。）两个阈值合起来的意思是：
"命中率超过 2%"或"命中率超过 0.5% 且错配很少"——后者是为了在低接头残留的数据上
也能认出来，但要求匹配得干净。

**第二段：从数据里从头找。** 表里没有的话，就利用"位置不同但内容相同"这一点：

1. 统计所有 read 在位置 $\ge 20$ 处的 10-mer 出现次数（跳过末尾 `shift_tail` 个碱基，
   末位很吵）；把 `AAAAAAAAAA` 的计数清零（polyA 尾巴会淹没一切）。
2. 排除三类显然是噪声的 k-mer：任一碱基出现 $\ge k-4$ 次（低复杂度）、
   G+C $\ge k-2$（过富 GC）、以 `GGGG` 开头（双色合成仪器的假象）。
3. 取计数最高的 10 个作为候选种子，从高到低试：出现次数 $< 10$、或富集倍数
   $< 20$ 倍就**停止**（不是跳过——候选是按计数降序排的，后面的只会更差）；
   种子自身相邻不同的碱基数 $< 3$ 个也跳过。
4. 用种子做锚点，向两侧各建一棵前缀树：向前挂"种子之后的序列"，
   向后挂"种子之前序列的反转"。每棵树上从根出发走"占优"子节点
   （占比 $\ge 0.95$、节点计数 $\ge 50$），走到走不动为止，两段路径加种子拼成接头。
5. 拼出来的接头回头和已知表对一次（要求**完全一致的前缀**）：能对上就返回表里那条
   完整序列，否则只有在"向后那棵树走到了尽头"（`reached_leaf`）时才返回拼出来的序列。

**两处必须原样保留的上游行为**（都在测试里守着）：

- **第二段在样本充分时经常给不出结果**。① 拼接时排除 read 末尾 1 个碱基，结果
  **缺末尾**；② 各条 read 的插入片段长短不一，向前那棵树在接头 3' 端因占比掉下来
  而提前停住。于是拼出来的序列短于已知表里的条目，吸附失败 → 返回"未检测到"。
  实测（合成数据、含接头的 read 占 20%）：2000 条样本 → 未检测到；1 万条 → 未检测到。
- **样本很小时会返回退化结果**：前缀树要求节点计数 $\ge 50$，含接头的 read 只有 40 条时
  两条路径都是空的，"接头"就等于那个 10-mer 种子。实测：300 条样本、40 条含接头
  → 返回 `GAAGAGCACA`（10 个碱基）。

一句话概括：**SE 数据上真正起作用的是第一段的已知接头表**，第二段更像兜底，
而兜底的成功率受上面两个几何因素限制。这正是上游文档建议 SE 用户直接给
`--adapter_sequence` 的原因。

#### 5.4.4.4 工程实现

**采样与内存。** 流式读文件、顺序取前若干条（上限 262144 条 / 4000 万碱基，
与上游一致），把**序列**留在内存里——接头检测要多次遍历同一批样本（先数 k-mer、
再围绕种子建两棵树），必须能随机访问。与上游的唯一差别：只留序列、丢掉质量串
（检测不看质量），内存因此省一半，判定结果不受影响。

**热路径用字节而不是字符串。** 序列与接头表在算法内部都是 `bytes`：
逐碱基比较、编码 k-mer 都是整数下标操作，比 `str` 快，也不需要处理编码问题。

**k-mer 过滤提前算并缓存。** 上游在计数之后遍历全部 $4^k$ 个键、逐个判断三类噪声；
这在 C++ 里无所谓，在 Python 里是实打实的开销（100 万个键 × 10 次位运算）。
这三条过滤**只与键本身有关、与数据无关**，因此本实现把它们提前算好并按 `key_length`
缓存，遍历顺序（升序）与上游相同，`total` 与 top-10 的结果不受影响。

**种子长度可调**（上游写死 10，允许 4\~12）。计数数组大小是 $4^k$ 字节：
$k=10$ 是 4 MB，$k=12$ 是 64 MB。可调主要是为了测试能跑得快些——改它不改变算法结构，
但会改变"什么算显著富集"的尺度。

**并列的取舍。** 上游用 `std::map` 存已知接头表，遍历顺序天然是字典序，
"命中数并列时取哪一条"依赖这个顺序。本实现显式对表排序，**结果与调用方传入的顺序
无关**，默认值下与上游逐位一致。

#### 5.4.4.5 验证记录

测试共 **30 项**（算法 20、文件级接口 8、真实数据 3），全部通过。

| 覆盖范围      | 内容                                                          |
| --------- | ----------------------------------------------------------- |
| 两段式阈值     | 已知表命中 / 不命中两侧（含 2% 与 0.5% 两条判定线）、接头长于 read 时跳过、空表等于跳过第一段    |
| 容错规则      | 每 16 个碱基允许 1 个错配（造 100 条各带 1 个错配的 read，全部命中）                |
| 并列取舍      | 两条接头命中数相同时返回字典序更小的那条                                        |
| 第二段的两种结局  | 样本充分 → 未检测到；样本很小（40 条含接头）→ 返回 10 碱基种子                       |
| 富集门槛      | 接头被稀释到 0.3% 时报不出结果                                          |
| k-mer 编解码 | 200 组随机数据的编码/还原往返、**滚动取值与"每窗口重算"完全一致**、含 N 的窗口无有效编码         |
| 采样与稳健性    | 条数 / 碱基数上限、gzip 输入（扩展名故意不写 .gz）、中文路径、缺失文件、FASTQ 截断、零长度 read |
| 真实数据      | 9 条记录 → 如实报"样本不足"；门槛降到 9 条也不凭空报接头                           |

**性能实测一：纯 Python 版**（本机、合成数据）：

| 场景                           | 耗时              |
| ---------------------------- | --------------- |
| 第一段：2000 条 read、已知表缩到 3 条、命中 | 0.28 s          |
| 第二段：2000 条 read、未知接头、跳过第一段   | 1.74 s          |
| 第二段：300 条 read、40 条含接头（退化结果） | 0.15 s          |
| 第一段：1 万条 read、全表 234 条       | 超过 30 s（未跑完即中止） |

**性能实测二：原生版**（同一台机器、10 万条 151bp 合成 read、全表 234 条）。
关键变量是**数据里有多少接头**——第一段的剪枝只在"已经找到高命中接头"之后才生效：

| 接头密度     |     第一段（全表） | 跳过第一段、只跑第二段 |
| -------- | ----------: | ----------: |
| 0%（干净数据） |  **16.4 s** |     0.085 s |
| 1%       |       2.5 s |      0.51 s |
| 20%      | **0.071 s** |       2.6 s |

三点结论：

1. **最坏情况是"没有接头"的数据**（16.4 s）：剪枝永不生效，234 条表 × 10 万条 read
   全扫一遍。上游 fastp 的同一段代码、同一个扫描上限（10 万条 read）也是这个量级，
   因此"不比上游慢"是满足的；但 16 秒对产品而言仍是刺眼的数字，优化办法见 $5.4.4.7$。
2. **有接头时快得多**（20% 密度下 71 ms）：剪枝一生效，表里绝大多数条目被跳过。
   第二段恰好相反——接头越多、富集的 k-mer 越多，建树开销越大。
3. **比纯 Python 快约两个数量级**：同一份 10 万条数据，Python 版在 1 万条时就已经
   超过 30 秒；原生版 10 万条最坏 16.4 秒、常见情形几十毫秒。

**对拍证据**（`common/native/tests/test_abi_adapter.py`，11 项全通过）：缩表下的
完整对拍（接头、来源、命中条数、采样规模一致）、默认全表在 500 条样本上命中
TruSeq 接头、空表跳过第一段后两侧给出同一个退化种子、干净数据两侧都"未检测到"
且原因文本一致、真实 9 条数据的"样本不足"措辞一致。另有一次性验证：500 条 read
用全表对拍（Python 4.6 s、原生亚毫秒），两侧接头与命中数完全相同。

#### 5.4.4.6 适用边界与已知限制

- **只处理单端 read**。双端数据靠 overlap 分析找接头（上游 `--detect_adapter_for_pe`），
  属于后续算法（双端 overlap）。
- **第二段常常给不出结论**（原因见 $5.4.4.3$）。要确定的结果，最稳的做法是直接指定
  接头序列（上游 `--adapter_sequence`，本实现对应 `adapters` 参数）。
- **纯 Python 版跑不动满量输入**（实测见上）。Python 侧只用于小样本与对拍，
  实际检测走原生层。
- **原生版最坏情况 16.4 s**：干净数据（没有接头）时第一段的剪枝永不生效，
  234 条表要扫满 10 万条 read。上游 fastp 同一段代码是同一量级，但对产品仍是刺眼
  的数字——优化思路记在 $5.4.4.7$；短期可用的缓解手段是把采样上限调小，
  或直接指定接头序列（跳过检测）。
- **已知接头表是快照**。表会随试剂盒更新，需要一条同步机制（上游每次发版更新）。
- **不做裁剪、不产出文件**。把接头从 read 上剪掉是下一个算法。
- **实际计算执行链路尚未接通**，广场入口只到契约层。

#### 5.4.4.7 待办

- **第一段最坏情况的优化（暂缓，方案已记下）**：干净数据下 10 万条 read 要 16.4 s。
  白羽奈绪已定"当前优化等级可以了，后续继续做"，因此这里只留方案不动手：给每条 read
  的每个位置取出 8-mer，用一张"8-mer（允许 $k$ 个错配）→ 候选接头"的索引，
  把"234 条逐个比对"换成常数级查表；$k = \lfloor \text{接头长度}/16 \rfloor$，
  因此不会漏掉任何真匹配。预期把最坏情况压到亚秒级。
- **在接头裁剪的入口里以选项形式暴露检测能力**（"接头来源：自动检测 / 手动指定"）——
  这是它撤掉独立入口之后的正式落点（$5.4.5$ 一并做）
