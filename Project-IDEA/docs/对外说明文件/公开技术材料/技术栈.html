CLIENT / 03

桌面客户端：Electron + React

桌面客户端我们使用了 Electron，理由是它能用一套 Web 技术栈同时管理界面、本地文件与系统能力，便于打包和跨平台发布。界面层使用 React 组织组件，配合 TypeScript 约束数据结构，避免界面字段与服务端返回互相漂移。构建工具使用 Vite，负责开发热更新与生产打包；编辑器使用 CodeMirror，提供多语言语法高亮和可扩展的编辑能力，我们在其中集成了代码编辑、Markdown 编辑与预览等常见开发场景。主进程负责窗口、文件读写、系统密钥存储与本地子进程，渲染进程只通过受限的 IPC 接口请求能力，这样的三层边界能让我们在不信任页面层的前提下开放本地能力。

已使用

Electron、React、TypeScript、Vite、CodeMirror、contextBridge 安全桥。

路径

继续桌面优先的路线：客户端作为唯一承载本地文件与硬件的入口，界面与核心逻辑保持可替换，为将来接入本地模型运行时预留位置。

SERVER / 04

服务端：FastAPI + Python

服务端我们使用 Python，因为它同时覆盖后端服务、数据清洗、科学计算与机器学习生态，单一语言可以减少跨栈协作成本。Web 层使用 FastAPI，自带异步接口与请求模型校验，适合流式输出与长任务；运行时由 Uvicorn 承载。数据库我们选择了 SQLite 作为当前主要持久化方案，保存会话、任务、记忆与授权记录，部署简单、事务可靠；配置使用 YAML 表达端口、模型与运行参数，敏感值通过环境变量注入。服务间或对外模型调用统一走 HTTPX，便于集中管理超时与连接池。模型接口按 OpenAI 兼容格式适配，保证未来替换不同供应商时，业务代码不需要大规模改动。

已使用

Python、FastAPI、Uvicorn、Pydantic、SQLite、YAML、HTTPX。

路径

保持轻量可自部署的服务形态；在数据规模增长后，再按需引入独立向量库与队列，而不是提前加重架构。

AGENT / 05

智能体与模型接入

智能体执行层我们围绕 Agent Runtime 组织：一个主调度角色负责理解目标、拆分步骤并汇总结果，多个专精角色分别承担科研分析、日常事务与创作等独立子任务。工具调用不是由模型自由发挥，而是先注册、再授权：文件、命令、网络等能力通过受控接口暴露，调用记录写入事件与审计，便于追溯与回滚。模型接入采用可替换设计，通过统一的模型客户端连接不同供应商，配置中保留多模型描述，未来可以按任务类型选择模型。Agent 之间与设备之间的任务交接使用快照与状态机表达，保证换一台设备或重启后任务仍可继续。

已使用

Agent Runtime、工具注册与权限判断、统一模型客户端、事件与审计记录。

路径

增加按任务类型路由模型，并探索让多个角色在共享记忆上协作，而不是简单把上下文全部拼进一次请求。

KNOWLEDGE / 06

知识检索与文献处理

知识检索我们使用 RAG 思路：先对文档做解析与切块，再建索引，检索时返回片段、来源与相似度，回答依据可回链到原文。当前轻量检索基于关键词与本地索引实现，接口上为向量检索预留了替换位置；当需要更强的语义匹配时，可以接入本地嵌入模型与向量存储。文献处理是面向科研场景的重点：我们希望把论文的摘要、方法、数据与结论拆成可检索的结构化字段，而不是把整篇 PDF 当作一大段文本；引用关系与证据链需要显式保存，让回答能说明结论来自哪篇文献的哪个部分。

已使用

文档导入、解析切块、关键词检索、带来源的引用回链。

路径

引入结构化文献解析与向量混合检索，让科研回答具备可核验的证据来源。

MEMORY / 07

长期记忆方向

记忆目前是分层存放：近期会话保存短期连续性，事实与证据按命名空间记录，每个条目带来源、状态与版本，可被修正或逻辑删除。现有记忆以结构化记录为主，配合关键词召回。下一阶段我们希望把重点放在记忆的自维护上：不是简单地越存越多，而是研究如何自动提炼重复信息、合并冲突事实、淘汰过期内容，并降低记忆对用户的干扰——即让记忆更像一个会自我整理的知识库，而不是无休止增长的日志。

已使用

分层记忆、命名空间隔离、证据与来源、revision 与召回上限。

路径

研究长期记忆的自维护算法：自动摘要、去重、冲突处理与遗忘策略。

EXTENSION / 08

插件与智能硬件扩展路径

插件方面，我们采用注册表式的扩展机制：插件集中登记，客户端统一管理开关，界面通过受控接口使用插件能力。这样插件不能越权访问未声明资源，卸载或禁用也能干净撤销。智能硬件方面，我们希望桌面客户端在未来承担本地控制中枢的角色：通过设备凭据与受控命令接口，向支持的外部设备下发指令并回收数据，同时保留权限审批与审计。当前先从软件接口规范做起，让插件的边界、硬件的抽象层与主程序解耦。

已使用

插件注册表、受控扩展接口、设备凭据与授权基础。

路径

定义标准化的硬件接入协议与设备能力抽象，使新设备通过插件即可接入，不改动核心。

SUMMARY / 09

小结

总体选型围绕一个原则：把需要可信边界的能力（本地文件、硬件、权限）收在桌面客户端与服务端的受控接口内，把变化最快的部分（模型、插件、知识解析）做成可替换的模块。当前已使用的技术栈足够支撑产品从通用助手走向科研、生活与创作三类场景；接下来的技术路径集中在四个方面：结构化文献处理与证据召回、长期记忆自维护、插件兼容标准、智能硬件接入抽象。
