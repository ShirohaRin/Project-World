01 · BACKGROUND

产品背景与问题成因

专业知识工作正在同时面对两类压力：一类来自材料规模持续增长，代码仓库、需求记录、研究资料、会议结论和临时脚本往往散落在多个目录与工具中；另一类来自任务节奏加快，用户需要在理解上下文后快速形成方案、修改文件、执行验证并向协作方解释依据。传统编辑器擅长处理文件，通用对话工具擅长生成文本，但二者之间常缺少统一的任务入口。用户不得不反复复制片段、补充背景、核对版本和确认执行范围，导致同一事实被多次描述，决策链条也难以回溯。 问题并不只是“信息太多”。当自动化能力开始接触本地文件、命令或外部接口时，真正需要被回答的是：它以什么身份工作、能够看到哪些项目、哪些操作应由人确认、执行结果如何留下证据、历史内容哪些可以继续复用。若这些问题没有显式设计，便利性会以边界模糊为代价。该环境因此把本地工作区、会话任务、受控工具、知识检索和长期记忆放在同一工作流中，目标是在不牺牲用户最终决定权的前提下，减少上下文切换和重复说明。相关设计还要求把可见界面、运行记录和数据状态对齐：用户看到的计划应能对应实际调用，调用产生的文件差异应能对应版本，检索返回的片段应能对应来源。这样做的意义不在于增加操作步骤，而在于让自动化结果具备可解释的证据链，便于专业人员复盘、纠错和交接。系统优先支持边界明确、结果可验收的任务，并把不确定性、失败原因和待确认事项保留在交付说明中。

02 · USERS

目标用户与使用场景

目标用户是需要在较长时间跨度内处理复杂上下文的技术与知识工作者，例如软件开发者、技术负责人、研究分析人员、项目协调人员，以及需要维护结构化文档的专业团队。他们通常不是只提出一个孤立问题，而是带着既有文件、明确约束、特定工作区和可验收结果进入任务：开发者希望在理解目录结构后完成一处修改并检查影响；研究人员希望把多份材料中的证据、假设与结论分开保存；负责人希望把讨论结论变成可跟踪的任务并明确责任边界。 对应的使用场景从本地编辑开始。用户选择已经授权的工作区，在 IDE 模式中浏览文件、阅读源码或维护文档；当任务需要组织目标、约束和产出时，可以转入工作台形成会话。智能体先根据用户给出的目标构造计划，再在允许的工具范围内检索、读取、编辑或执行。用户可以检查每一步输入、输出和生成结果，并决定是否采纳。对需要长期积累的内容，近期消息、可复用事实和专题资料不会混为一谈：会话用于保持当前任务连续，记忆用于保存有范围的事实，知识库用于提供可追溯材料。平台不把“任何人、任何目录、任何操作都可自动完成”作为承诺，而是优先服务于愿意明确目标、接受复核并重视数据边界的用户。对于团队而言，还需关注任务交接时新成员能否仅凭运行记录理解上下文、决定依据和剩余风险，从而把个人效率转化为可共享的工程资产。还应记录输入资料的版本、参与人员的确认动作和最终采用的产物，避免交接只依赖口头说明。只有当这些信息能够被检索、比较和复用，工作台才真正承担知识协作基础设施的职责，而不是把聊天记录换一种展示方式。

03 · WORKFLOW

端到端工作流

一次任务从“选择上下文”开始，而不是从空白输入框开始。用户先在客户端选择 IDE 或工作台模式，并打开已授权的本地工作区；随后描述目标、已知条件、不可触碰的范围和验收标准。系统将这些显式信息与当前会话、必要文件和可用工具组合为任务上下文。智能体在获得指令后先拆分步骤：哪些内容需要读取，哪些判断需要用户提供依据，哪些修改需要进入文件，哪些验证可以在受控环境完成。计划不是隐含过程，而应当能够被用户理解和调整。 执行阶段遵守工具和项目两层限制。文件访问只在工作区白名单内进行，命令、网络或其他能力通过受控注册入口暴露，而不是由会话文本直接获得。每个阶段返回中间结果、必要依据和任务状态，用户可在关键点复核，再决定继续、修订或停止。完成后，结果包括实际修改、验证说明和仍待确认的限制；如果发现具有复用价值的事实，可按来源和范围写入相应记忆或知识层。这样，当前任务不会因为窗口结束就完全丢失，也不会把未经确认的聊天内容自动当成长期事实。工作流的核心是把意图、权限、执行和证据连起来：用户始终拥有最终决策权，自动化只在明确边界内承担辅助执行。任务状态还应能被机器读取，便于前端恢复、自动化测试和运营观测；对不可重试的操作必须记录明确原因，避免系统在不确定时重复产生副作用。当任务包含多个交付物时，系统还应维护它们之间的关系，例如需求与实现、实现与测试、资料与引用、结论与假设。用户不必接受不可解释的黑箱式完成状态，而可以沿着任务记录回到原始输入和具体工具结果。对于需要人工判断的节点，系统应明确标记“待确认”并停止扩大执行范围；对于可以自动验证的节点，则应保存命令输出、版本信息或结构化检查结果。对于跨阶段任务，系统还应保留输入快照与产物版本之间的关联，保证后续重试使用的是已确认上下文而不是漂移后的临时状态。

04 · CLIENT

客户端：本地 IDE 与工作台

客户端采用桌面应用形态，技术基础为 Electron、React、TypeScript 与 Vite。IDE 模式面向本地文件工作：用户可选择工作区、查看文件树、打开和保存文件，并在编辑器中处理 TypeScript、JavaScript、Python、JSON、HTML、CSS、Markdown、Java、C++、Go、Rust、YAML 与 XML 等常见文本格式。Markdown 支持编辑、源码查看和同步预览，便于把技术说明与代码维护放在相近的操作路径中。桌面能力经由主进程与安全 IPC 桥接，避免页面层直接拥有不受控的系统能力；工程已具备 Windows x64 的目录式打包配置。 工作台模式承载任务导向交互，包括聊天式离线会话、智能体选择器和上下文工具栏。它的作用不是复制一个普通聊天页面，而是让用户在提出任务时仍能看见工作区、文件和后续结果。客户端还保留本地插件市场、插件开关与视觉设置入口，扩展由集中注册表管理。当前边界同样清晰：离线版本启动时不默认连接服务端、智能体宿主或线上数据服务，因此在线协作、云端记忆和跨设备执行不是桌面端的既有默认能力。客户端首先保证本地编辑体验和清晰交互，再通过受控接口对接需要的服务能力。 从实现角度看，客户端还承担状态呈现与用户确认职责。文件树、编辑器、预览区和任务面板应共享当前工作区标识，但不能因此把全部文件内容预加载到页面；大型仓库宜按目录和打开动作渐进读取，减少启动耗时与敏感数据暴露。主进程负责窗口、文件系统和进程边界，渲染进程只通过 Preload 暴露的最小接口请求能力，消息应携带请求标识、工作区信息和结果状态，便于界面处理并发与取消。对文件修改，界面应展示目标路径、变更摘要和保存结果；对命令或外部服务请求，则先呈现范围、参数和风险，再等待用户确认。这样的客户端不是单纯的展示层，而是把授权意图、执行进度和可回滚结果转换为用户可以理解的交互证据。

05 · SERVER & AGENT

服务端与智能体协作

服务端提供智能协作的执行基础，包含 Python 与 FastAPI 接口、会话和消息持久化、模型客户端、智能体执行循环、任务调度、受控工具注册，以及基于本地 SQLite 的记忆基础。接口层负责接收已经认证的请求并返回统一结果；会话层保存任务连续性；执行循环负责把目标、上下文、工具结果和模型响应组织成可继续推进的过程。工具注册是重要控制点：文件读取、内容编辑、搜索或命令执行不应由自由文本直接决定，而应被包装为可识别、可限制、可记录的能力。 在服务端层面，任务对象、运行对象和工具调用对象需要拥有稳定标识、状态转换和关联关系。这样才能在流式输出中区分增量文本、工具事件、错误和最终产物，也才能在重连后恢复用户看到的状态。长任务应进入异步队列，普通交互不被批处理阻塞；模型供应商变化应由适配层吸收，业务层只依赖统一的完成、流式和健康检查契约。运行时的每一项自动化能力都必须有明确的失败出口和人工接管点。服务端还需要区分用户取消、策略拒绝、工具异常、模型不可用和数据冲突等错误类型，使客户端可以采取不同恢复动作，并让监控指标反映真实原因而非笼统的失败数量。对于工具调用，还应校验参数结构、工作区归属和调用者身份，避免模型输出成为绕过策略的隐式入口。角色设计采用总调度与专精角色分层。总调度角色负责理解目标、拆解任务、汇总材料和形成最终建议；项目管理、科研分析、智能体生产等专精角色分别处理独立子任务，不继续调度其他角色，从而避免责任链无限扩展。这里需要区分角色定义与运行时能力：目录中存在某个角色描述，并不等于客户端已经动态加载、版本管理并完整编排了该角色。当前已具备服务端执行基础和若干专精实现，但运行时装配、扩展加载、完整对话入口与跨设备设备代理仍属于需要继续验证的范围。对外描述以实际可进入的接口、可运行的流程和可复核结果为准，不把设计设想表述为完成状态。服务端还应对运行预算、并发数量、工具调用次数和任务超时进行限制，防止单个请求占用全部资源；当模型返回无法解析的工具参数时，应回退到人工确认或安全失败，而不是猜测执行。 为保证工程可运维，服务端还应把每次运行拆成可观测事件，而不是只保存最后一段回答。事件至少需要关联会话、任务、角色、工具和产物，记录开始时间、结束时间、耗时、状态及错误类别；敏感参数只保留脱敏摘要。调度器需要支持幂等提交、取消和有限重试，重试前判断工具是否具有副作用，避免重复写入或重复执行外部动作。模型上下文装配应区分用户输入、检索证据、工具返回和系统策略，防止不可信文本覆盖更高优先级约束。对于生成的文件和引用，应保存版本关系与校验结果，使客户端能够明确展示“已完成”“部分完成”或“等待确认”。这些机制共同把智能体从一次性文本生成器变成可审计的执行组件，也为后续压测、故障定位和能力评测提供统一数据基础。

06 · KNOWLEDGE & MEMORY

知识与记忆的分层设计

知识与记忆不是单一的“更长上下文”。近期会话保存用户与系统围绕当前任务交换的消息，用于维持短期连续性，但其中的猜测、临时方案和未确认结论不能自动成为长期事实。本地记忆模块以 SQLite 等存储基础承载数据、索引和视图，为检索和管理提供可观察的落点。专题知识库则按材料主题组织，例如世界观、正文、设计和补充资料，使召回可以依据任务范围选择来源，而不是将所有文本一次性塞入输入。记忆核心的 domain、evidence、recall 等模块强调事实归属、证据来源与召回过程。 分层带来两项直接收益。第一，用户可以区分“本次会话说过什么”“哪些内容已被确认”“结论依据来自哪些材料”，减少把模型生成内容误当作原始证据的风险。第二，权限控制可以跟随数据范围：只读检索接口提供 memory_search 与 memory_get，调用凭据独立且可以撤销；客户端不保存检索密钥，也不直接连接记忆存储。当前已有本地记忆与受控只读检索的基础，长期云端记忆、完整跨设备协作和更复杂的写入治理仍需在服务端能力成熟后逐步验证。记忆系统的关键不是保存得越多越好，而是能够回答“这条内容从哪里来、何时形成、适用于谁、是否仍然可信”。候选事实需要经过确认、合并、质疑或归档等生命周期处理；召回时先做授权、时间和状态过滤，再进行关键词与向量的混合排序，并受上下文预算限制。这样既减少历史倾倒，也让纠错可以影响后续使用而不抹去审计轨迹。对于写入型学习任务，应保存幂等键、版本号和处理结果，保证后台失败可以重试而不会重复生成事实；用户删除或否定内容后，后续召回也必须尊重这一状态。

07 · AUTHORIZATION

权限与信任边界

安全设计从身份、项目和工具三层同时开始。身份层中，桌面客户端使用账号会话，自动化客户端使用签发的设备凭据；凭据应当独立、可轮换、可撤销，而非把固定敏感信息写入应用。项目层中，服务端依据已登录身份与项目权限决定可访问范围，新增工作区必须显式登记，智能体不能因为任务文本中出现一个路径就自行扩大可见目录。工具层中，文件、命令、网络和其他系统能力通过受控工具注册与权限上下文暴露，可为不同调用方配置不同能力边界。三层共同避免“已经登录”被误解为“可以操作所有资源”。 记忆访问遵循同样的隔离原则。客户端不保存知识检索密钥，不直接连接记忆数据库；需要云端数据时，经由服务接口完成身份校验、范围判断和审计。已授权工作区限定于事先登记的代码、配置、共享知识服务或独立站点项目，具体范围应由服务端策略维护而不是由界面自行判断。当前公开材料只说明这种控制模型及其已验证的只读路径，不披露私有目录、账号信息、密钥或内部数据。需要强调的是，权限系统不是一次性开关：每新增一种工具、数据源或设备能力，都应重新定义主体、对象、动作、证据和撤销路径，并通过测试验证不会形成并行绕过通道。权限判定还应发生在实际执行前，而不是只在界面显示一个允许状态；服务端应再次核对会话有效期、项目归属、工作区白名单、工具参数和资源版本。审计记录至少保留谁在何时以何种身份请求了什么动作、策略如何判定以及结果是否成功，敏感字段以摘要或脱敏形式保存。发生凭据泄露、成员变更或项目关闭时，撤销应立即阻断后续调用，并能追溯已产生的任务和产物。

08 · STATUS

当前状态与交付边界

当前可以明确说明的能力包括：在 Windows 桌面端进行本地 IDE 编辑和 Markdown 预览；在工作台中组织离线任务会话；在服务端运行接口、会话、模型客户端、工具和本地记忆基础；在受控身份与权限下验证只读记忆检索；以及使用 Git 同步公开代码与经过处理的文档。客户端的工作区、编辑器、预览、插件入口和桌面桥接属于可见实现，服务端的会话、任务与工具循环属于可检查的基础。对于这些能力，仍应以具体入口、测试结果和版本范围确认，不应仅凭目录名称或设计文稿做结论。 同样重要的是不能直接宣称的部分：桌面端并非默认接入在线智能体或云端记忆；尚不应表述为已经可远程操作主力设备的文件、命令、图形计算资源、屏幕或其他客户端；所有角色定义也并非都已动态加载并完成编排。跨设备自动执行、完整在线对话入口、生产部署加固和正式签名的 Windows 安装体验仍需要进一步交付与验证。边界说明并不是削弱价值，而是建立可信预期：已具备的能力可以被复现，尚在建设的能力有明确前置条件，任何涉及权限扩大或私有数据的功能都必须先完成安全和验收检查。交付边界还意味着版本化管理：每次发布都应说明客户端版本、服务端版本、模型或工具版本、支持的平台和已知限制；文档中的“当前”不能脱离时间和测试环境单独理解。对于尚未形成稳定入口的研究方向，可以保留技术路线和验证计划，但必须与可复现能力分开排版。只有这样，计算机专业人士才能根据材料判断系统的真实成熟度，并据此设计集成、评测或试用方案。

价值与后续验证

该工作环境的价值在于把开发、资料处理和智能协作从彼此割裂的工具链重新组织为连续工作流。对个人用户，它减少在目录、编辑器、聊天窗口和笔记之间重复搬运背景的时间，并让任务结果附带过程和依据；对团队用户，它使工作区范围、会话上下文、资料来源与工具能力更容易被解释和复核；对维护者，它把客户端体验、服务端执行、记忆治理和权限策略分成可以独立演进却能共同约束的层次。价值不依赖夸大自动化程度，而依赖在明确限制下稳定完成真实任务。 下一阶段验证应围绕可观察结果展开：确认客户端到服务端的受控连接是否保留身份与项目范围；确认每种工具在拒绝、允许和撤销时的行为一致；确认记忆检索能返回与来源相符的材料而不越过用户范围；确认角色协作在失败、超时或信息不足时能够把问题交回用户；确认公开交付不包含私有数据、静态凭据或未验证能力。通过这些验证，系统可以逐步扩展更多工具与协作方式，同时保持“默认最小权限、用户最终确认、结果可追溯”的原则。公开介绍的目的不是承诺无边界的自动化，而是说明一个可持续建设、可验证并且尊重专业判断的技术方向。评价体系还需要覆盖不同类型的真实任务，而不仅是演示路径：包括陌生仓库理解、跨文件修改、资料引用、权限拒绝、服务中断和结果回滚。每项评价都应固定输入范围、工具集合、模型版本和验收标准，并保存可比较的运行记录。只有当这些指标在声明范围内稳定，系统才适合扩大用户、数据源或工具种类；否则应把失败归因和限制公开保留。
