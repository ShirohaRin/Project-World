# Project IDEA 项目架构

## 1. 文档定位

本文定义 Project IDEA 的产品与技术架构，用于统一 Project World 长期智能协作基础设施、科研智能体平台和 IDEA Assistant 桌面端的研发方向。

它不是某一版本的部署手册，也不替代内部立项企划书。内部立项材料以生物科技文献调研与综述为一期切入点；本文描述支撑这一切入点，并能继续承载创作、开发、项目管理、跨设备协作和新产品孵化的通用架构。

## 2. 项目定义

Project IDEA 是 Project World 的智能协作子项目。它由统一工作台、智能体运行时、知识与记忆服务、模型接入层及设备协作能力组成。

项目的首期交付聚焦于科研场景中的文献调研、论文解读、证据组织和综述草案生成。长期来看，平台还应支持世界观与小说创作、文档和演示制作、代码与工具开发、资料整理、自动化工作流、生活协作及新子项目的快速接入。

核心目标不是把所有能力堆叠在一个聊天窗口中，而是建立一套能持续积累任务上下文、知识资产、交付物和工作方法的工作环境。

## 3. 架构原则

### 本地优先，服务协同

桌面端应在离线状态下保持工作区浏览、文件编辑、Markdown 预览和由本机环境支持的基础运行等核心能力。在线服务负责智能体推理、跨设备同步、长期知识、任务编排和异步处理；服务不可用时，客户端明确显示降级状态，不伪造在线结果。

### 任务优先于单轮对话

对话是入口，不是全部。每个复杂请求可逐步形成可查看的任务、输入资料、运行记录、中间产物、引用、版本和最终交付物，从而让长周期的研究、创作和开发工作可以继续、复盘和复用。

### 模型可替换

Agent Runtime 只面向统一模型契约编程。云端 API、官方 SDK、OpenAI 兼容接口和未来独立服务器上的自托管模型都通过 Provider 适配；替换模型不应改写客户端交互、Agent 工作流、任务数据或知识结构。

### 知识可追溯

科研回答、综述、研究计划和重要创作资料应保留来源、版本、引用片段和生成上下文。系统需要区分原始资料、已整理知识、模型推断和待验证假设，避免把生成文本误当作事实库。

### 能力可组合

文档、代码、设计、科研、项目管理和跨设备操作建立在同一任务和工具协议上。新能力优先作为工具、Skill、Agent 或工作流接入，而不是为每个新场景重新建设一套应用。

## 5. 交互与工作层

### IDEA Assistant 桌面端

当前桌面端采用 Electron、React、TypeScript、Vite 和 CodeMirror 构建，是 Project IDEA 的第一工作入口。它承担本地工作区选择、文件树、编辑器、Markdown 多视图、IDE/Work 模式、基础运行命令和在线会话界面。

桌面端分为两个进程边界：

| 部分 | 职责 |
|---|---|
| React 渲染层 | 编辑器、文件树、对话、任务面板、设置与运行结果呈现 |
| Electron 主进程 | 本地文件系统、系统能力、窗口生命周期、安全 IPC 与在线会话保存 |
| Preload 桥接 | 向渲染层暴露最小化、类型明确的本地能力接口 |

未来 Web 与移动端复用 Platform API、事件协议、任务模型和知识服务，不复用桌面端的本地文件实现。桌面端仍然是复杂开发和创作任务的主入口。

### IDE 与 Work 模式

`IDE` 模式面向代码、文件、构建与调试；`Work` 模式面向自然语言任务、研究资料、创作过程、运行进度与交付物。两种模式共享当前工作区、任务引用和上下文，但以不同的界面组织方式呈现。

这种划分避免把代码工作台做成单纯聊天应用，也避免将研究与创作流程限制在传统 IDE 的文件视图中。

## 6. 平台服务与任务模型

平台服务是客户端与智能体运行时之间的稳定边界。它当前提供 HTTP API，并以统一流式事件接口为目标，管理会话、任务、Agent Run、工具调用记录、异步状态和可恢复的工作结果。

```text
用户输入或工作区事件
        ↓
Conversation
        ↓
Task
        ↓
Agent Run
        ↓
Plan / Tool Call / Knowledge Query / Model Response
        ↓
Artifact、Citation、Run Log、Task State
```

建议的核心对象如下：

| 对象 | 作用 |
|---|---|
| `Conversation` | 保存连续交互及其关联任务 |
| `Task` | 表达可执行、可取消、可恢复的工作单元 |
| `AgentRun` | 一次 Agent 编排执行的完整生命周期 |
| `ToolCall` | 记录文件、命令、检索、网络、设备等工具调用 |
| `Artifact` | 文档草案、代码、报告、表格、图片、构建产物等可交付结果 |
| `Citation` | 结果到资料、片段、页码或数据版本的回链 |
| `StreamEvent` | 客户端实时显示的文本增量、状态变化、工具事件和错误 |

短对话可直接完成；长文献解析、批量索引、跨文献综述、构建和训练评估应进入异步队列。在线交互与长任务分开调度，避免一项长工作阻塞普通对话。

## 7. Agent Runtime

Agent Runtime 将自然语言目标转化为受控的工作步骤。它不以“自动完成一切”为目标，而是用计划、上下文、工具和验证环节完成可检查的协作过程。

```text
任务输入
  → 上下文装配
  → 任务规划
  → 选择 Agent 与 Skill
  → 调用知识、工作区或计算工具
  → 归纳与验证
  → 生成结果与引用
  → 写入运行记录和交付物
```

当前定义层包含四个核心 Agent：

| Agent | 主要职责 |
|---|---|
| IDEA | 复杂问题统筹、长期协作、项目与创作支持 |
| IDEA ProgramWorldAdminister | Project World 项目结构、计划、归档与执行协调 |
| IDEA Researcher | 文献阅读、科研分析、证据比较与研究材料整理 |
| IDEA AgentProducer | 新 Agent、Skill、工具链与评测样例的设计和维护 |

定义层的角色卡与系统说明位于 `Agents/`；运行时需要逐步为每个 Agent 补齐模型策略、工具清单、知识集合、示例任务、评测集和版本信息。角色定义不应直接等同于可执行代码，运行时装配以可测试配置为准。

## 8. 模型路由与未来训练接口

模型路由层为所有 Agent 提供统一调用接口：

```text
capabilities()              返回上下文、视觉、工具调用和流式能力
complete(request, context)  返回标准完整响应
stream(request, context)    返回标准化流式事件
health()                    返回可用性、延迟与版本
```

推荐的 Provider 类型：

| Provider | 场景 |
|---|---|
| `openai_compatible` | 当前兼容 Chat Completions 的云端模型服务 |
| `sdk_provider` | 必须使用特定官方 SDK 的模型服务 |
| `self_hosted` | 未来独立服务器上的推理网关与自托管模型 |

当前模型服务可以作为 `openai_compatible` Provider 接入。未来训练服务器不直接嵌入主服务，而是通过独立推理网关暴露标准接口，再作为 `self_hosted` Provider 加入路由池。

模型演进以评测结果驱动：先优化任务定义、资料质量、检索、重排序、提示与工具验证；只有当这些环节已得到验证且复杂推理仍构成稳定瓶颈时，才升级模型规模、增加 GPU 或开展 LoRA/SFT。训练与在线推理保持独立演进，避免训练任务破坏日常服务稳定性。

## 9. 知识与记忆服务

### 知识服务

知识服务负责将论文、PDF、世界观资料、小说设定、项目文档、代码说明和其他资料转换为可检索、可引用的知识单元。

科研资料的典型处理链路如下：

```text
资料导入
  → 格式解析与元数据提取
  → 正文、图表、表格、图注、参考文献结构化
  → 分块、嵌入、关键词索引
  → 混合检索与重排序
  → 证据片段、页码和引用信息返回给 Agent
```

一期 RAG 不应只保存向量文本。每个知识单元至少保留原始来源、标题、作者、时间、文档版本、页码或章节位置、解析状态和引用关系。对于科研输出，Agent 需在结果中标出资料事实、跨资料推断和待验证假设。

### 记忆服务

记忆服务保存跨会话可复用的结构化上下文，而不是机械地保存全部聊天记录。建议分为以下类型：

| 类型 | 典型内容 |
|---|---|
| 会话记忆 | 当前任务摘要、近期文件、未完成步骤 |
| 项目记忆 | 架构决策、术语、目标、版本与里程碑 |
| 创作记忆 | 世界观设定、人物关系、剧情状态、文风约定 |
| 科研记忆 | 已验证结论、文献卡片、研究问题、评测反馈 |
| 工作偏好 | 常用工具、输出格式、工作节奏与个人化约定 |

长期记忆的写入应经过提炼、去重和版本化处理。记忆服务必须支持检索、修订、导出、删除和失效标记，避免过期事实持续影响后续任务。

## 10. 工作区与跨设备协作

Project World 的开发不固定于单一机器或单一产品。系统以工作区、项目、任务和产物为协作单位，而不是以某台设备的目录结构作为全部事实来源。

设备代理负责把本地能力抽象为统一动作：

| 能力域 | 典型操作 |
|---|---|
| 工作区 | 列目录、读写文件、查看 Diff、管理项目产物 |
| 终端 | 运行构建、测试、脚本与受限开发命令 |
| 屏幕理解 | 获取截图、OCR、识别可见界面状态 |
| 输入协作 | 在明确任务步骤下完成界面输入与交互 |
| 同步 | 上传任务状态、产物版本、运行日志与设备状态 |

跨设备实现应分阶段推进：先同步会话、任务和文件元数据，再加入受控工作区动作，最后才扩展屏幕理解和交互自动化。每次设备动作都需要产生可回看结果，网络中断时保留待同步状态而非静默丢失。

## 11. 科研能力域

科研是 Project IDEA 的首期验证场景。系统重点不是替代实验或专业判断，而是缩短资料整理、证据核对、结构化阅读和研究材料起草的时间。

一期能力链：

```text
研究问题
  → 主题检索与资料归类
  → 论文结构化解读
  → 证据卡片与观点比较
  → 综述提纲和草案
  → 人工审阅、修订与归档
```

后续能力按基础成熟度扩展：实验方法总结、候选方案辅助、数据清洗与统计、可复现代码、图表解释、专用 Skill、模型适配和评测工具。所有科研输出需要维持证据链与不确定性表达，不能替代实验验证、临床判断或既有科研流程。

## 12. Project World 能力域

Project World 是持续演进的创造项目，Project IDEA 为其提供通用的智能协作底座。除科研外，优先支持以下工作流：

| 能力域 | 主要工作 |
|---|---|
| 世界构建 | 整理设定、梳理时间线、发现矛盾、维护概念关系 |
| 小说与文章 | 大纲、角色弧线、章节草稿、资料核对与版本比较 |
| 美术与音乐 | 创意说明、素材整理、制作任务、风格与资产记录 |
| 游戏与数字产品 | 需求拆解、设计文档、代码协作、构建与测试 |
| 项目管理 | 里程碑、待办、依赖、复盘、文档归档与跨项目关联 |
| 日常协作 | 计划安排、信息整理、设备间工作续接与提醒 |

新出现的子项目只需注册工作区、资料集合、任务模板和所需 Agent/Skill，即可复用底层会话、运行时、知识服务和模型路由，而不需要重新建设独立平台。

## 13. 当前实现基线

当前工程已经具备以下基础：

| 模块 | 当前状态 |
|---|---|
| 桌面工作台 | Electron + React + TypeScript；支持工作区、文件编辑、Markdown、多视图、IDE/Work 模式与基础运行 |
| 平台服务 | FastAPI 服务、会话与任务接口、SQLite 持久化基础与运行日志；统一流式事件协议仍在收束 |
| Agent 执行 | LLM 调用、工具注册、文件/命令/网络工具和基础 Agent Runner |
| 模型接入 | 当前可接入 OpenAI 兼容服务；后续迁移为统一 Provider 契约 |
| 账号会话 | 邮箱验证码、短期访问令牌、刷新会话和桌面端安全存储已经具备基础实现 |
| 邮件投递 | 自建本机 SMTP 与 DKIM 签名已部署；域名 SPF、DKIM、DMARC 与 PTR 记录仍需完成发布与验收 |

当前仍需优先完成的工程收束包括：将进程内会话和任务完全迁移到持久化数据模型、统一流式事件协议、建立 Agent 配置加载机制、完成 Knowledge Adapter、引入异步任务队列，并补足端到端测试与运行观测。

## 14. 分阶段路线

| 阶段 | 建设重点 | 可验证产出 |
|---|---|---|
| A. 平台基础 | 桌面端、服务 API、账户会话、任务对象、运行日志 | 客户端可稳定连接服务并恢复任务上下文 |
| B. 知识与科研 MVP | 文献导入、解析、混合检索、引用、调研与综述工作流 | 可完成带来源的文献调研和综述草案 |
| C. 运行时成熟 | Agent 配置、工具协议、流式事件、队列、观测与评测 | 长任务可恢复，失败可诊断，结果可复盘 |
| D. 跨设备协作 | 设备代理、工作区动作、任务同步、产物版本 | 工作可在多设备间续接并保留执行记录 |
| E. 多能力域 | 世界构建、创作、开发、设计、自动化与专用 Skill | 新子项目能复用共同底座快速接入 |
| F. 模型与训练演进 | 自托管推理网关、专用小模型、LoRA/SFT、独立训练环境 | 模型替换与训练实验由评测数据驱动 |

每个阶段以前一阶段的可用性、可观测性和真实任务反馈为进入条件。功能数量不是完成标准；能够稳定完成真实工作、保留过程资料并支持后续迭代，才是阶段交付的判断依据。

## 15. 关键质量指标

| 维度 | 关注指标 |
|---|---|
| 工作体验 | 首次响应时间、任务完成率、跨模块切换成本、离线可用范围 |
| 知识质量 | 检索命中、引用完整度、引用正确性、过期资料识别率 |
| 科研价值 | 论文解读完整度、综述可编辑性、专家审阅反馈、资料整理时间变化 |
| 工程可靠性 | 构建与运行成功率、任务恢复率、错误可定位率、服务可用性 |
| 模型效果 | 固定评测集表现、工具调用成功率、事实/推断/假设区分质量 |
| 可演进性 | 新模型、新 Agent、新知识集合、新工作区的接入成本 |
